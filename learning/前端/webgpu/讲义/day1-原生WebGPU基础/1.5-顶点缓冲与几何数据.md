# 1.5 顶点缓冲与几何数据

> Day 1 · 模块 5 · 约 90 分钟
> 理论对照：《GAMES101 现代计算机图形学课程笔记》第 4 章「光栅化」——三角形是基本图元，顶点数据是它的输入侧

demo 01 的全部几何只有三个顶点，而且写死在 WGSL 源码里。想让浏览器渲染一个 Blender 导出的模型，几十万个顶点不可能塞进着色器源代码——更不可能每改一次模型重编一次着色器。数据必须走另一条路：放在 JS 的类型化数组里，一次上传到 GPU 显存，draw 的时候由管线按声明好的布局逐顶点拉取。这条路就是顶点缓冲，本模块用两个新 demo（02 与 03）把同一个四边形画两遍——先 interleaved 布局，再索引绘制——把数据组织方式的账算清楚。

## 数据与代码的分界

顶点数据放代码里有三个死穴。产量上，顶点色、UV、法线这些资产由 DCC 工具产出，天然是数据文件而非代码片段。更新上，改一个顶点色要重新编译整个 shader module，而改 buffer 内容只动 20 字节的上传。语义上，数据可以在 CPU 与 GPU 之间流动（顶点动画、GPU 粒子回读），代码只会凝固在编译时刻。WebGL 时代你就熟悉这条分界（`vertexAttribPointer` + `bufferData`），WebGPU 把它显式化成一份布局声明：`arrayStride` 与 `offset` 全部按字节计算，类型用 `format` 字符串声明，声明一次挂在管线上，取数逻辑全部交给硬件。

## interleaved 布局与字节算术

一条顶点记录可以有两种存法。interleaved 把一个顶点的所有字段连续存放，整个模型一块 buffer；separate 把同一种字段集中存放，position 一块、color 一块。创意网站默认选前者：一次 `writeBuffer` 全量上传、顶点字段相邻对缓存友好、状态切换少。separate 的用武之地是字段更新频率不同的时候——比如把每实例变化的属性单独拆出去配 `stepMode: 'instance'`，这是 Day 3 之前会反复出现的优化模式。

demo 02 的每个顶点是 5 个 float32：`[x, y, r, g, b]`，一个顶点 20 字节。字节图如下，`arrayStride` 与两个 `offset` 的关系一目了然：

```text
interleaved 布局：一个顶点 = 连续 20 字节（demo 02）
arrayStride = 20 ──────────────────────────────────────────────▶
┌───────── vertex 0 ──────────────┐┌──────── vertex 1 ─▶
│   x   │   y   │   r   │   g   │   b   │   x   │  ...
│  4B   │  4B   │  4B   │  4B   │  4B   │  4B   │
└───────┴───────┴───────┴───────┴───────┴───────┴────
▲                       ▲
offset 0                offset 8
format: float32x2       format: float32x3
（position 属性）        （color 属性）
```

三个数字全部来自字节算术：stride 是 5 个字段 × 4 字节；position 从字节 0 开始；color 越过 2 个 float（8 字节）开始。js 侧的准备就是把这些字节装进 `Float32Array`，上传到一块带 `VERTEX` 用途的 buffer。

## index buffer：让顶点只存一次

画一个四边形要两个三角形、六个顶点位，但几何上只有四个点。索引绘制把「六个顶点位」换成「四个顶点 + 一份下标表」：顶点 buffer 存 4 份完整记录，index buffer 存 `[0, 1, 2, 0, 2, 3]`，图元装配按索引取顶点。

| | 非索引（demo 02） | 索引（demo 03） |
|---|---|---|
| 顶点数 | 6 | 4 |
| 顶点 buffer | 120 字节 | 80 字节 |
| 索引 buffer | — | 12 字节 |
| 总上传字节 | 120 | 92 |
| 共享顶点的变换 | 算 2 次 | 算 1 次 |
| 改对角线颜色 | 改 2 处顶点数据 | 改 1 处 |

四边形的节省看着温吞，规模一放大就是另一个故事：`(n+1)×(n+1)` 的网格，非索引要写 `6n²` 个顶点，索引只要 `(n+1)²` 个顶点外加 `6n²` 个 2 字节下标。除了空间与带宽，索引还有一个图形学层面的价值：共享顶点意味着共享法线，平滑着色的球、连续的波浪面都依赖它；反过来，需要硬边的立方体边角仍要拆成重复顶点——Day 2 的 `procedural-geometry` demo 会现场权衡这件事。

## How：demo 02 与 demo 03 对照精讲

两个 demo 的初始化、uniform、帧循环完全一致，全部差异集中在「数据怎么组织」与「draw 怎么取数」。先看 demo 02 的数据段，interleaved 数组直接可读：每行一个顶点，颜色按对角线从紫排到青，左下与右上各重复出现一次：

```ts
const vertices = new Float32Array([
  // x      y     r  g  b
  -H, -H, ...VIOLET, // 左下（第 1 个三角形）
   H, -H, ...MID,    // 右下
   H,  H, ...TEAL,   // 右上
  -H, -H, ...VIOLET, // 左下（第 2 个三角形）
   H,  H, ...TEAL,   // 右上
  -H,  H, ...MID,    // 左上
]);

const vertexBuffer = device.createBuffer({
  size: vertices.byteLength, // 6 顶点 × 20 字节 = 120 字节
  usage: GPUBufferUsage.VERTEX | GPUBufferUsage.COPY_DST,
});
device.queue.writeBuffer(vertexBuffer, 0, vertices);
```

`usage` 里的 `VERTEX` 是管线的取数许可证，缺了它 `setVertexBuffer` 就是 validation error。`COPY_DST` 允许 `writeBuffer` 写入——queue 的上传操作本质上是一次 GPU 侧拷贝。

布局声明挂在管线的 `vertex.buffers` 数组上，与 ASCII 图逐项对应：

```ts
buffers: [
  {
    arrayStride: 5 * 4, // 20 字节：跨过一个顶点的全部数据
    attributes: [
      { shaderLocation: 0, offset: 0, format: 'float32x2' }, // position
      { shaderLocation: 1, offset: 8, format: 'float32x3' }, // color
    ],
  },
],
```

`shaderLocation` 是与 WGSL 的 `@location(n)` 对表的槽位号；`format` 声明这段字节的解释方式（几个 float、是否归一化）。渲染时把 buffer 接到 0 号槽，顶点数交给 `draw`：

```ts
pass.setVertexBuffer(0, vertexBuffer); // 0 对应 vertex.buffers[0]
pass.draw(6); // 两个三角形共 6 个顶点
```

demo 03 的改动一共三处。数据段从 6 行变 4 行，多出一块 12 字节的索引 buffer：

```ts
const indices = new Uint16Array([
  0, 1, 2, // 左下 → 右下 → 右上
  0, 2, 3, // 左下 → 右上 → 左上
]);

const indexBuffer = device.createBuffer({
  size: indices.byteLength, // 6 索引 × 2 字节 = 12 字节
  usage: GPUBufferUsage.INDEX | GPUBufferUsage.COPY_DST,
});
```

索引类型按数据选：顶点数 65535 以内用 `Uint16Array` 配 `'uint16'`，超过换 `Uint32Array` 配 `'uint32'`。渲染段多一行 `setIndexBuffer`，`draw` 换 `drawIndexed`：

```ts
pass.setVertexBuffer(0, vertexBuffer);
pass.setIndexBuffer(indexBuffer, 'uint16'); // 索引格式随数据类型
pass.drawIndexed(6); // 6 个索引 = 两个三角形
```

两份 WGSL 一字不差——`@location(0)` 里的 `vec2f` 照样由硬件按布局填充，顶点是被 `positions` 直接生成还是被索引间接指认，着色器无从得知也无需知道。索引的全部影响止步于图元装配之前，这是它能「无痛替换」的原因。

## 常见坑

| 报错/症状 | 原因 |
|-----------|------|
| `arrayStride must be a multiple of 4 bytes` | stride 填了元素数（5）而不是字节数（20）；`arrayStride: 5 * 4` 这种写法能把单位写进表达式 |
| `The sum of byteOffset and byteLength ... exceeds arrayStride` | attribute 的 `offset` 越过顶点边界，通常是 color 的 offset 算成了元素数 2 而非字节 8 |
| 错误面板出现 vertex buffer 用途相关 validation error | `createBuffer` 的 usage 漏了 `GPUBufferUsage.VERTEX`，管线无权读取 |
| `Index buffer format ... doesn't match` | `setIndexBuffer` 的位宽（`'uint16'`）与数据类型（`Uint32Array`）不配对 |
| 画面缺一个三角形或顶点错乱 | 索引表漏项、顶点数与 `draw`/`drawIndexed` 数量对不上 |
| 颜色出现周期性条纹 | `offset` 没有落在 4 字节边界上（attribute offset 必须是 4 的倍数），或 format 分量数与数据不符 |

## Checkpoint

- 能画出一个 `[x, y, r, g, b]` 顶点的 20 字节布局图，标出 stride 与两个 offset
