# 2.7 GPGPU 粒子与动画模拟

> Day 2 · 模块 7 · 约 60 分钟
> 理论对照：《GAMES101 现代计算机图形学课程笔记》第 8 章「动画与模拟」——欧拉积分、显式与半隐式、数值稳定性

iyO 官网用 160 万颗粒子拼出品牌字，鼠标划过时文字像被水流冲开又愈合；igloo 的页脚让几千颗粒子在光标周围聚散。这类效果的共同骨架是一条状态机：位置 + 速度 → 力场 → 积分 → 新的位置 + 速度。CPU 跑一万粒子要榨干一个核心，GPU 上这是 compute shader 的一帧零头。本模块把 2.6 的零件组装成完整的粒子模拟，规模一万——这个数字足够建立直觉，又小到让你看清每一环。

## 状态机与双缓冲

粒子是有记忆的对象：它的下一步由当前位置和速度共同决定。模拟循环因此是一个标准的「读状态 → 算力 → 积分 → 写状态」状态机，GAMES101 第 8 章把它写成 `x' = x + v·dt`、`v' = v + a·dt`——欧拉积分。demo 里用的是半隐式版本（先更新速度再用新速度更新位置），它在弹簧这类系统里数值上稳定得多，显式欧拉会越弹越大。

读写的分离靠 2.6 立好的双缓冲概念落地：两个一样大的 storage buffer，帧 N 读 A 写 B，帧 N+1 读 B 写 A。关键认知藏在 JS 侧——交换的从来不是 buffer 内容，是绑定组里指向谁的「指针」。两组绑定组提前建好，每帧换着挂：

```ts
const computeBindGroups = [0, 1].map((i) =>
  device.createBindGroup({
    layout: computePipeline.getBindGroupLayout(0),
    entries: [
      { binding: 0, resource: { buffer: states[i] } },       // src：只读
      { binding: 1, resource: { buffer: states[1 - i] } },   // dst：可写
      { binding: 2, resource: { buffer: simBuffer } },
    ],
  }),
);
```

WGSL 侧的声明一读一写，地址空间天然防住了「读写同一个元素」的竞争：

```wgsl
@group(0) @binding(0) var<storage, read> src: array<Particle>;
@group(0) @binding(1) var<storage, read_write> dst: array<Particle>;
```

## 粒子的存储：vec4f 不是浪费

粒子的 struct 有一个用血泪换来的约定——全部用 `vec4f`：

```wgsl
struct Particle {
  pos: vec4f, // xyz 位置；w 未用。用 vec4f 而非 vec3f：std430 下
  vel: vec4f, // xyz 速度；w 未用。vec3f 会按 16 字节对齐，JS 侧难对
};
```

storage 地址空间默认 std430 布局，`vec3f` 按 16 字节对齐、实际占 12 字节，两个 `vec3f` 打包出来的 struct 步长与字段偏移和 C 直觉对不上——JS 侧按 24 字节一个粒子打包，WGSL 侧实际按 32 字节步进读，粒子全部错位，画面表现为「一团乱码且无报错」。`vec4f` 让每个字段天然 16 字节对齐，浪费的 4 字节买回字节数学的确定性。对照讲义 1.6 的 uniform 对齐规则：同一个坑换了地址空间再踩一遍。

## 噪声场：完整可抄的 simplex

粒子系统的气质几乎全由力场决定，而力场的骨架是噪声。value noise（2.6 已用）在低频区有可察觉的网格感，simplex 把插值空间从方形格子换成单形（simplex），维度越高优势越大，3D 场景默认选它。以下是从 demo 06 的 `particles.wgsl` 截出的完整版本，Ashima Arts / Stefan Gustavson 的经典移植，逻辑逐字未动——直接抄进你自己的项目：

```wgsl
fn mod289v3(x: vec3f) -> vec3f {
  return x - floor(x * (1.0 / 289.0)) * 289.0;
}

fn mod289v4(x: vec4f) -> vec4f {
  return x - floor(x * (1.0 / 289.0)) * 289.0;
}

fn permute4(x: vec4f) -> vec4f {
  return mod289v4(((x * 34.0) + 1.0) * x);
}

fn taylorInvSqrt4(r: vec4f) -> vec4f {
  return 1.79284291400159 - 0.85373472095314 * r;
}

fn snoise(v: vec3f) -> f32 {
  let C = vec2f(1.0 / 6.0, 1.0 / 3.0);
  let D = vec4f(0.0, 0.5, 1.0, 2.0);

  let i = floor(v + dot(v, C.yyy));
  let x0 = v - i + dot(i, C.xxx);

  let g = step(x0.yzx, x0.xyz);
  let l = 1.0 - g;
  let i1 = min(g.xyz, l.zxy);
  let i2 = max(g.xyz, l.zxy);
  let x1 = x0 - i1 + C.xxx;
  let x2 = x0 - i2 + C.yyy;
  let x3 = x0 - D.yyy;

  let pi = mod289v3(i);
  let p = permute4(permute4(permute4(
    pi.z + vec4f(0.0, i1.z, i2.z, 1.0)
  ) + pi.y + vec4f(0.0, i1.y, i2.y, 1.0)
  ) + pi.x + vec4f(0.0, i1.x, i2.x, 1.0));

  let n_ = 0.142857142857;
  let ns = n_ * D.wyz - D.xzx;

  let j = p - 49.0 * floor(p * ns.z * ns.z);
  let x_ = floor(j * ns.z);
  let y_ = floor(j - 7.0 * x_);

  let x = x_ * ns.x + ns.yyyy;
  let y = y_ * ns.x + ns.yyyy;
  let h = 1.0 - abs(x) - abs(y);

  let b0 = vec4f(x.xy, y.xy);
  let b1 = vec4f(x.zw, y.zw);

  let s0 = floor(b0) * 2.0 + 1.0;
  let s1 = floor(b1) * 2.0 + 1.0;
  let sh = -step(h, vec4f(0.0));

  let a0 = b0.xzyw + s0.xzyw * sh.xxyy;
  let a1 = b1.xzyw + s1.xzyw * sh.zzww;

  let g0 = vec3f(a0.xy, h.x);
  let g1 = vec3f(a0.zw, h.y);
  let g2 = vec3f(a1.xy, h.z);
  let g3 = vec3f(a1.zw, h.w);

  let norm = taylorInvSqrt4(vec4f(dot(g0, g0), dot(g1, g1), dot(g2, g2), dot(g3, g3)));
  let n0 = g0 * norm.x;
  let n1 = g1 * norm.y;
  let n2 = g2 * norm.z;
  let n3 = g3 * norm.w;

  var m = max(0.6 - vec4f(dot(x0, x0), dot(x1, x1), dot(x2, x2), dot(x3, x3)), vec4f(0.0));
  m = m * m;
  return 42.0 * dot(m * m, vec4f(dot(n0, x0), dot(n1, x1), dot(n2, x2), dot(n3, x3)));
}
```

`snoise` 返回一个标量场。想要向量场（每个位置一个漂移方向），标准做法是三次偏移采样——三个标量场拼成一个 `vec3f`，这就是 demo 06 的用法；要 curl 噪声（无散度、更像流体）就对它取旋度，公式照搬、采样点错开即可。噪声数学的完整背景在《Three.js 创意 3D 课程笔记》第 12 课，这里不重推。

## 鼠标与渲染：storage 直读顶点

交互力的通道是 uniform：鼠标世界坐标与按下状态每帧写进 `simBuffer`，compute 里按距离算引力或斥力。`select(a, b, cond)` 是 WGSL 的三元表达式，按住与松开一个分支搞定：

```wgsl
let toMouse = u.mouse.xyz - p;
let dm2 = dot(toMouse, toMouse);
let pull = select(-0.10, 1.7, u.mouse.w > 0.5) / (dm2 + 0.30);
accel += toMouse / sqrt(dm2 + 1e-4) * pull;
```

渲染端的技巧是把 storage buffer 直接当顶点来源。渲染管线不配任何顶点缓冲，顶点着色器 `var<storage, read>` 直读粒子数组——compute 写完、render 直读，数据不离开显存，连 copy 都省了：

```wgsl
@group(0) @binding(0) var<storage, read> particles: array<Particle>;

@vertex
fn vs(@builtin(vertex_index) vi: u32, @builtin(instance_index) ii: u32) -> VOut {
  // ...
  let pt = particles[ii]; // 实例号当粒子号：一个实例 = 一颗粒子
  // ...
}
```

`draw(6, COUNT)` 一次画完：6 个顶点来自 `vertex_index`，粒子数据来自 `instance_index`。WebGPU 没有 `gl_PointSize`，point-list 图元恒为 1 像素——想要肉眼可见的粒子，只能自己把每个粒子展开成一个小 quad，这与图元的选择无关，而是 API 的硬约束。demo 06 选 6 顶点 quad（两个三角形拼四边形）而不是 point-list，理由有两层：quad 能在片元里画柔边圆点做辉光，point-list 给不了任何形状控制；quad 尺寸可以随深度透视缩放，星星有远近层次。

## How：demo 06 逐段精讲

```bash
npm run dev
# http://localhost:5173/demos/day2/06-particle-simulation/index.html
```

初始化在 JS 里做一次：三条旋臂加高斯散布摆出星系盘，切向初速度按 `0.5 / sqrt(r)` 给——近快远慢，画面从第一帧起就在转：

```ts
const init = new Float32Array(COUNT * 8);
const gauss = () => Math.random() + Math.random() + Math.random() - 1.5;
for (let i = 0; i < COUNT; i++) {
  const r = Math.pow(Math.random(), 0.62) * 1.75 + 0.04;
  const theta = (i % 3) * ((Math.PI * 2) / 3) + r * 2.2 + gauss() * 0.16;
  const k = i * 8;
  init[k] = Math.cos(theta) * r + gauss() * 0.05;                    // x
  init[k + 1] = gauss() * 0.045 * (1.1 - Math.min(r * 0.35, 0.7));   // y
  init[k + 2] = Math.sin(theta) * r + gauss() * 0.05;                // z
  const vOrb = 0.5 / Math.sqrt(r + 0.12); // 近快远慢的切向初速度
  init[k + 4] = -Math.sin(theta) * vOrb;
  init[k + 6] = Math.cos(theta) * vOrb;
}
device.queue.writeBuffer(states[0], 0, init);
```

compute 的力场在噪声之外再叠一层「星系涡旋」：切向推进加向心束缚，把粒子轻轻压回盘面。渲染的帧循环把双缓冲一轮走完整——compute 读 `cur` 写 `1 - cur`，渲染读 `1 - cur`，帧尾交换：

```ts
const cpass = encoder.beginComputePass();
cpass.setPipeline(computePipeline);
cpass.setBindGroup(0, computeBindGroups[cur]);
cpass.dispatchWorkgroups(Math.ceil(COUNT / 64));
cpass.end();

// 渲染：必须读刚写完的 1-cur——双缓冲交换时绑定组要跟着换
const rpass = encoder.beginRenderPass({ /* ... */ });
rpass.setPipeline(renderPipeline);
rpass.setBindGroup(0, renderBindGroups[1 - cur]);
rpass.draw(6, COUNT);
rpass.end();

device.queue.submit([encoder.finish()]);

// 交换：下一帧读刚写完的那个
cur = 1 - cur;
```

颜色在片元里按速度映射：黑 → 深蓝 → 电蓝 → 白，四段 smoothstep。加法混合（`one / one`）让重叠的粒子天然叠出辉光，并且与绘制顺序无关——这也是渲染管线不带深度测试的原因，一万颗半透明星星的排序问题直接被混合模式消灭。

## 常见坑

| 报错/症状 | 原因 |
|-----------|------|
| 粒子每帧「抖回」上上帧的位置 | 双缓冲交换了，渲染绑定组没跟着换（读到了旧 buffer）；渲染必须读 `1 - cur` |
| 粒子炸成一团乱码、控制台无报错 | JS 按 `vec3f`×2 = 24 字节打包，WGSL 侧 struct 实际步长 32——用 `vec4f` 或手动补 padding |
| 一半粒子永远不动 | `dispatchWorkgroups` 直接给了粒子总数：107 个 workgroup 应该是 `ceil(10000 / 64)`，总量要除 workgroup_size |
| 粒子只有 1 像素、肉眼几乎不可见 | 想当然用了 point-list：WebGPU 的点恒为 1 像素且无 point size，必须展开 quad |
| 画面全白糊成一片 | 加法混合下亮度溢出：粒子亮度或直径超了，色带末端别直接给 1.0 |
| 粒子越跑越快最后飞散 | 显式欧拉在不稳定力场下发散；换半隐式欧拉、加阻尼、限制 dt 上限 |

## Checkpoint

- 能画出双缓冲一个完整帧的读写图，说清「交换的是绑定组不是 buffer」
- 能解释 `vec4f` struct 约定背后的 std430 对齐规则，算出 1 万粒子的 buffer 字节数
- 能把 `snoise` 的三次偏移采样拼成一个漂移向量场，并说出 curl 噪声的用途
- 能解释 storage buffer 直读顶点的工作方式，以及 `draw(6, COUNT)` 里两个数字各自的来源
