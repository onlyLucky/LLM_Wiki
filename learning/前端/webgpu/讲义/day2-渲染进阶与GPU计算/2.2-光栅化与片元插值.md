# 2.2 光栅化与片元插值

> Day 2 · 模块 2 · 约 1 小时
> 理论对照：《GAMES101 现代计算机图形学课程笔记》第 4 章「光栅化」（4.1 采样 / 4.2 判断点在三角形内 / 4.5 深度缓冲）

demo 01 的立方体有 24 个顶点，顶点着色器每帧只跑 24 次；画布上被它覆盖的像素数以万计，每个像素的颜色却都「有出处」。中间发生的事叫光栅化：把三个裁剪坐标之间的连续三角形，翻译成一串离散的片元，再把顶点上携带的属性摊到每个片元上。这个模块拆开翻译机的两级齿轮——三角形级别的「谁能进」与像素级别的「值是多少」，然后拿 demo 01 做三组「改一行看效果」的实验。

理论侧的完整版在笔记第 4 章：为什么三角形是基本图元、怎么用叉积判断点在三角形内、采样为什么会走样。Z-Buffer 的算法描述在笔记 4.5。这些推导不在这里重复，本模块的落点是 WebGPU 管线里对应的三件事：cull mode、varying 插值、depth 精度。

## 图元装配与背面剔除

顶点流进入固定功能段的第一站是图元装配：按 topology（`triangle-list`）每三个下标拼一个三角形。拼出来的每个三角形都有一个「绕序」——三个顶点在屏幕上的旋转方向。WebGPU 默认 `frontFace: 'ccw'`：从观察者一侧看，逆时针绕序的三角形算正面。绕序再加上空间位置就有了一个免费的优化：闭合形体的背面永远被正面挡住，可以在光栅化之前整片扔掉。

| cullMode | 剔除谁 | 典型用途 |
|-----------|--------|---------|
| `'back'` | 背面三角形 | 默认值；闭合物体的标准配置，约省一半三角形 |
| `'front'` | 正面三角形 | 剖视图；看到物体内壁，本模块实验一会用到 |
| `'none'` | 谁都不剔 | 不闭合的几何（平面、粒子）、需要双面着色的面片 |

剔除发生在屏幕空间判定之前，被剔除的三角形连片元着色器都不会跑，属于「白拿」的性能。代价是绕序必须诚实：demo 01 的每个面用 `ids` 数组从外侧看逆时针排出四角，六面共享同一份约定。绕序一旦排错，cull mode 就会把该留的剔掉、该剔的留下——症状极有戏剧性，实验一会现场看到。

demo 01 的数据段里，绕序直接写在面的顶点下标里：

```ts
const FACES = [
  { ids: [4, 5, 6, 7], color: rgb('#4C6FFF') }, // 前 +z 电蓝
  { ids: [1, 0, 3, 2], color: rgb('#8B5CF6') }, // 后 -z 紫
  { ids: [5, 1, 2, 6], color: rgb('#2DD4BF') }, // 右 +x 青
  { ids: [0, 4, 7, 3], color: rgb('#F59E0B') }, // 左 -x 琥珀
  { ids: [7, 6, 2, 3], color: rgb('#E8ECF4') }, // 上 +y 主白
  { ids: [0, 1, 5, 4], color: rgb('#8FA5FF') }, // 下 -y 浅蓝
];
```

值得对照的是 `-z` 那面：角点顺序 `[1, 0, 3, 2]` 与 `+z` 面的 `[4, 5, 6, 7]` 方向相反。同一份角点表在两个面里要反向取，因为「从外侧看」的两个外侧方向相反——绕序是观察者相关的量，这正是它携带朝向信息的原因。

## 视口变换：NDC 到像素的最后一棒

2.1 的变换链图末端是屏幕空间。视口变换把 NDC 的 x、y ∈ [-1, 1] 映射到 [0, width] × [0, height]，把 y 翻转（NDC 的 y 向上、屏幕的 y 向下），z 保持 [0, 1] 原样传给深度测试。笔记 4 章开头的「像素中心在 (x+0.5, y+0.5)」约定也在这级生效——光栅化判定片元归属时采样的是像素中心。

在 WebGPU 里这一步默认按画布尺寸自动完成，平时无需过问；需要渲染到画布的一个子区域（后处理链的中间目标）时用 `pass.setViewport(x, y, w, h, minDepth, maxDepth)` 显式声明。demo 02 的 mipmap 生成就是反向利用了「viewport 默认是整张附件」这一点——把小一级的 mip 层当附件，采样着色器画一个大三角形，自然铺满整层。

## 重心坐标与 varying 插值

三角形内部的属性值从哪来：重心坐标。屏幕内任意一点 P 都可以写成三个顶点的加权组合 `P = αA + βB + γC`（α + β + γ = 1），三个权重的几何意义是子三角形面积比，完整定义与计算公式见笔记第 5 章「重心坐标」一节。插值就是拿同一组权重去混合顶点属性：

```text
V = α·V_A + β·V_B + γ·V_C
```

WebGPU 里这件事零代码：顶点着色器往 `@location(n)` 输出的任何值，到片元着色器的同名 `@location(n)` 输入时，都已经被硬件按重心坐标插值过。这类值叫 varying。demo 01 的立方体每面颜色均匀，奥妙在数据组织：颜色属于面，而角点被三个面共享，8 个角点存不下面色——于是展开成 24 个顶点，同面四角给同一种颜色，插值混合同一颜色的结果还是它本身。反过来，把某个面的四个角点改成四种颜色，整面立刻变成平滑渐变，改的只有数据。

## 透视校正插值：为什么插的是 1/w 加权

varying 插值有一个透视埋下的陷阱。重心坐标是在屏幕空间里算的，但直接拿屏幕权重混合「3D 侧的属性值」，在透视投影下是错的：

```text
透视为什么破坏屏幕空间插值（一维示意）

3D 空间（均匀）            屏幕空间（透视压缩，远处堆在一起）
A ──── M ──── B            A ─ M' ──────── B
0    0.5    1               0  ~0.66        1

3D 的中点 M 投影后落在 M'：屏幕比例不再等于 3D 比例，
按屏幕权重插值会把 M 的属性安到错误的片元上
```

远处的物体被压缩得更密，屏幕上的「一半」对应的不再是 3D 里的一半。如果插值 UV，贴图会歪；插值颜色，渐变会错位；插值法线，光照会偏。

硬件的解法是透视校正插值：屏幕空间里直接对 `属性/w` 与 `1/w` 做线性插值，然后相除。可行性来自透视除法的对偶性质——w 本身（以及任何除以 w 的量）在屏幕空间是线性的，于是除法把非线性恰好抵消。推导见笔记第 5 章「重心坐标」一节的透视校正说明，记住结论就够日常使用：WebGPU 对 `@location` varying 的插值默认就是 perspective-correct，你拿到的片元属性已经校正过，一般没有理由关闭它。

顺带一提深度值：`@builtin(position)` 的 z 分量在片元侧也是插值来的，而插的正是 NDC 深度——它已经是「除过 w」的量，可以直接比较远近，Z-Buffer 的裁决就建立在它上面。

## Z-Buffer 与 z-fighting

深度测试的算法在笔记 4.5：每个像素记录当前最小深度，新片元只有更近才覆盖颜色与深度。`depth24plus` 给每个像素 24 位定点深度，听着很多，但透视投影把深度值按 1/z 非线性摊进 [0, 1]——near 附近极密，far 附近极疏。精度问题的两个常见来源：

| 来源 | 机制 | 后果 |
|------|------|------|
| far/near 比值过大 | 深度区间被 near 附近的小段垄断 | 远处物体深度量化误差放大 |
| 几何共面或近共面 | 两个表面深度差小于量化步长 | 同一像素上互抢胜负，帧间闪烁 |

第二个就是 z-fighting：两个几乎重叠的表面，深度值四舍五入后相同或交错，`'less'` 比较随浮点噪声翻面，肉眼看就是边缘闪烁。传统 API 有 polygonOffset 可以把某个表面沿深度方向推一点，WebGPU 没有这个机制——排查思路只有两条：收紧投影范围（near 尽量推远、far 尽量拉近，减小比值），或者直接调几何把共面的面错开。创意网站里「地面网格与地面本体闪」「贴地阴影与地面闪」都属于这一族，记住「先查 near」这个条件反射。

## How：三组改一行的实验

实验对象是 demo 01。每组只改一处，刷新后观察。

实验一：`cullMode: 'front'`——立方体被剖开。在 `main.ts` 的管线声明里把 `cullMode: 'back'` 改成 `'front'`：

```ts
primitive: { topology: 'triangle-list', cullMode: 'front' },
```

看到的现象：无论从哪个角度拖，你看到的永远是立方体的「内壁」，像走进了一个只有外壳的房间。正反面判定整体翻转后，原本被挡住的内侧翻到可见。这个模式在调试几何时很好用——绕序错误导致的「面消失」用它一测便知：如果 `'front'` 模式下消失的面出现了，说明那面的绕序排反了。

实验二：`cullMode: 'none'`——前后表面同屏竞争。改回 `'back'` 再改成 `'none'`：

```ts
primitive: { topology: 'triangle-list', cullMode: 'none' },
```

现象几乎看不出变化：立方体外观照旧，因为深度测试把该挡的照样挡了。区别在成本——背面的片元也全部光栅化并跑了一遍片元着色器，输给深度测试才被丢弃。此实验的意义是搭好实验三的舞台：此刻立方体前后表面在同一批像素上都有片元，深度裁决第一次变得肉眼可见。

实验三：`near: 0.1` 改成 `0.0001`——深度精度崩塌，z-fighting 现身。保持实验二的 `'none'`，把透视矩阵的近平面推近三个数量级：

```ts
const proj = mat4Perspective(
  (50 * Math.PI) / 180,
  chrome.width / chrome.height,
  0.0001, // near 从 0.1 推近到 0.0001：深度区间被近平面垄断
  100,
);
```

现象：立方体表面开始闪烁、碎裂，拖动视角时更明显。near 缩小一千倍后，[0, 1] 深度区间的前一小段被 [0, 0.0001] 占据，立方体前后表面（距相机 3 到 6 个单位）的深度差被量化步长吞掉，`'less'` 比较在两个表面间随机翻面。把 far 从 100 拉到 5000 会得到同一类症状，方向相反。修法照旧：near 尽量大、far 尽量小，让 far/near 落在几百以内。

## 常见坑

| 报错/症状 | 原因 |
|-----------|------|
| 立方体从外面看像被剖开、永远看到内壁 | `cullMode` 与绕序不匹配：要么把 `'back'` 误设成 `'front'`，要么某面的 ids 顺序排反 |
| 某个面凭空消失（其余正常） | 那一面的顶点下标写成了从外侧看顺时针，被 `'back'` 错误剔除 |
| 两个贴在一起的表面互相闪烁 | z-fighting：共面几何或 far/near 比值过大；WebGPU 无 polygonOffset，错开几何或收紧投影范围 |
| 透视视角下插值出来的 UV / 颜色错位 | 绕过 varying 手动用屏幕坐标推属性（如在 fs 里用 `position.xy` 折算 UV），没有经过透视校正；把属性放进 `@location` 交给硬件 |
| 面片闪烁随相机移动忽好忽坏 | 深度量化误差边缘：先检查 near 是否被设得过小 |
| 帧率无端掉一截 | `cullMode: 'none'` 用在了闭合物体上，背面片元白白光栅化 |
