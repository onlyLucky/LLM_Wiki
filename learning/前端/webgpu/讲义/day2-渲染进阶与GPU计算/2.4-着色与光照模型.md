# 2.4 着色与光照模型

> Day 2 · 模块 4 · 约 1 小时
> 理论对照：《GAMES101 现代计算机图形学课程笔记》第 5 章「着色」（5.1 Blinn-Phong 反射模型 / 5.2 着色频率）

demo 02 的立方体贴上了蓝图，但光是假的：明暗调子来自一个写死的光照方向，无论怎么拖拽视角、怎么滚轮缩放，受光面与背光面纹丝不动。真实感来自「表面回应光」——光源动了、视线动了、表面朝向变了，颜色都要跟着变。demo 03 把这件事做全：立方体与地面组成的小场景里，琥珀色主光贴着鼠标绕立方体滑动，冷色补光固定在高位背侧，高光收得很紧，暗部始终有环境光兜底，最后经 gamma 修正输出。整个画面像展厅里打灯的雕塑，而支撑它的只是三个向量的点积。

公式的推导（Lambert 余弦定律、平方反比衰减、半程向量为什么能替代反射方向）全部在笔记 5.1，本模块把结论拿过来直接落地，重心放在三件 WebGPU 侧的事：法线从顶点流到片元的路、光照 uniform 的组织、以及输出前的 gamma 修正。

## Blinn-Phong 三分量

模型的完整形式一句话能写下：片元颜色 = 环境光 + 漫反射 + 高光。

| 分量 | 公式 | 物理直觉 |
|------|------|---------|
| 环境光 | `L_a = k_a · I_a` | 常数项，近似被忽略的间接光照，填住全黑阴影 |
| 漫反射 | `L_d = k_d · (I / r²) · max(0, n·l)` | Lambert 余弦定律 + 平方反比，与视线无关 |
| 高光 | `L_s = k_s · (I / r²) · max(0, n·h)^p` | 半程向量 h = normalize(l + v)，指数 p 收窄波瓣 |

三个输入向量都在着色点上定义：n 是法线、l 指向光源、v 指向相机。漫反射只看 n 与 l 的夹角——正对着光的表面吃满能量，掠射面按余弦打折，背光面被 `max(0, ·)` 截到零。高光部分用半程向量替代反射方向：观察方向越接近镜面反射，h 越接近 n，`n·h` 越大；指数 p 把宽泛的余弦峰压窄，demo 03 取 90，高光收成一小块。推导与各参数的视觉对照图见笔记 5.1。

模型是经验的，但它对「光源数」天然开放——每个光源独立算一份漫反射与高光再累加即可。demo 03 挂两个：暖主光负责叙事，冷补光强度只有 0.16，专职把暗部从死黑里捞出来一点。

## 着色频率：为什么在片元里算

同一套公式可以在三个粒度上执行，笔记 5.2 把它们叫着色频率：flat（每三角形一色）、Gouraud（每顶点算一次、插值到面内）、Phong（每片元算一次）。粒度取决于顶点密度——三角形足够小的时候 flat 也能看着光滑，而顶点稀疏时 Gouraud 会把恰好落在三角形内部的高光整个丢掉。

WebGPU 的 `@fragment` 阶段天生就是 Phong 频率：每个片元都有插值来的法线、位置、视线可用，成本只是「着色次数多」。三个 demo 的演进正好踩过这条线——demo 01 的面色在顶点数据里写死（flat 的手工版），demo 02 在 vs 里算一个固定方向的调子再插值（Gouraud 的退化版），demo 03 把完整光照搬进 fs。顺带一个命名陷阱：Phong shading（着色频率）与 Blinn-Phong（反射模型）是两个维度的概念，前者说「在哪算」，后者说「算什么」。

## 法线为什么要乘逆转置矩阵

法线要参与光照，就必须从模型空间变换到世界空间——光源和相机的位置都定义在世界空间。直觉的做法是把 model 矩阵直接乘上去，而这个做法在非均匀缩放下是错的。法线与切向量永远正交（n·t = 0），变换后的法线 n' 与切向量 t' = M·t 要继续保持正交，代入 n'·t' = 0 可以解出唯一的 n' = (M⁻¹)ᵀ·n——法线矩阵是 model 的逆转置，左上 3×3 就够（法线是方向量，平移无效）。

非均匀缩放的破坏力值得一秒想象：沿 x 拉伸两倍的立方体，正面法线 (0, 0, 1) 用 model 变换后仍是 (0, 0, 1)，但侧面的法线 (1, 0, 0) 与被拉伸后的几何已经不再垂直——光照算在一个歪掉的方向上，明暗边界整体错位。两个特例让这个坑平时不显形：纯旋转是正交矩阵，转置恰等于逆；均匀缩放下逆转置与原矩阵只差一个标量系数，归一化后等价。demo 02 的 model 只有旋转，所以它敢直接 `u.model * vec4f(normal, 0.0)`；demo 03 把缩放、平移都叠进 model，就必须老老实实算逆转置。

## 多光源 uniform 的对齐陷阱

双光源意味着 uniform 里出现数组，这正是 1.6 对齐规则最容易咬人的地方。WGSL 的 uniform 地址空间里，`array<vec3f, N>` 的每个元素按 16 字节步进存取——vec3f 本身 12 字节，末尾 4 字节是空洞；而 JS 侧如果按「每光源 12 字节」打包 `Float32Array`，两边就错位 4 字节，第二个光源的数据整体串位，画面症状是颜色怪异、亮度异常。

demo 03 的解法是直接放弃 vec3f 数组，改用 `array<vec4f, 2>`，多出来的 w 分量不浪费——装光源强度：

```wgsl
struct Frame {
  vp: mat4x4f,
  // xyz = 位置，w = 强度。用 vec4f 而非 vec3f：vec3f 数组实际按
  // 16 字节步进存取，末尾 4 字节是空洞，直接用 vec4f 免去手写 padding
  lights: array<vec4f, 2>,
  cameraPos: vec4f, // xyz = 相机位置，w = 时间
};
```

顺带的设计：两个绑定组按「变化频率」分工。`@group(0)` 是帧级的 Frame（相机与光源，每帧一写，场景里所有物体共享），`@group(1)` 是物体级的 Obj（model 与 normalMatrix，立方体、地面、光源标记各一份）。切物体只切 group 1，相机光源的数据不动——这个分组模式在 Day 3 的 Three.js 里会以 `uniforms` 的 update 语义再次出现。

## gamma 与 sRGB

一个容易被忽略的事实：光照公式全部工作在线性空间，而显示器的响应曲线接近 `输出亮度 ∝ 输入值^2.2`。着色算出的 0.5 直接写进帧缓冲，屏幕实际发出的亮度只有理想值的 73% 左右，画面整体发闷偏暗。修正办法是在输出前做一次幂运算：`pow(color, vec3f(1.0 / 2.2))`，把线性值升到显示器的编码空间。demo 03 的两处片元出口都做了这一步：

```wgsl
// gamma 修正：着色在线性空间算完，写回 sRGB 显示要取 1/2.2 次幂
return vec4f(pow(color, vec3f(1.0 / 2.2)), 1.0);
```

这里埋着一个 Day 3 之前不展开的话题：纹理资产本身通常是 sRGB 编码的，严格管线要在采样时先转回线性（`rgba8unorm-srgb` 格式）。demo 的程序化纹理按线性近似处理，视觉上已经足够自洽；工程化管线里这是必须补上的一环，3.5 的后处理模块会回来清算。

## How：demo 03 精讲

### 几何：法线属于面，24 顶点的第二个理由

立方体的每个顶点被三个面共享，而三个面的法线各不相同——法线与 2.2 的面色一样属于「面」。于是 24 顶点再登场，每顶点携带 position(3) + normal(3) + material(1)，顶点布局 `arrayStride: 28`。material 是一个分支标记：0 是立方体、1 是地面，让同一份 WGSL 按材质走不同参数。地面用 4 个顶点直接把世界坐标烘焙进顶点数据，model 保持单位阵，省掉一份数学。

### 法线矩阵：伴随矩阵除以行列式

JS 侧求逆转置用的是经典伴随矩阵法：每个元素换成代数余子式，整体除以行列式。均匀缩放加旋转时它与 model 只差标量，数值上稳定：

```ts
// 法线矩阵：model 左上 3×3 的逆转置（伴随矩阵 / det）。
// 均匀缩放 + 旋转时它等于 model 本身；非均匀缩放时必须用它，
// 否则法线方向会被掰歪（讲义 2.4 的重点坑）
function mat4NormalFromModel(model: Float32Array): Float32Array {
  const a00 = model[0], a01 = model[4], a02 = model[8];
  const a10 = model[1], a11 = model[5], a12 = model[9];
  const a20 = model[2], a21 = model[6], a22 = model[10];

  const c00 = a11 * a22 - a12 * a21;
  const c01 = a12 * a20 - a10 * a22;
  const c02 = a10 * a21 - a11 * a20;
  const det = a00 * c00 + a01 * c01 + a02 * c02 || 1;
  const inv = 1 / det;

  const m = new Float32Array(16);
  m[0] = c00 * inv;
  m[1] = (a02 * a21 - a01 * a22) * inv;
  m[2] = (a01 * a12 - a02 * a11) * inv;
  m[4] = c01 * inv;
  m[5] = (a00 * a22 - a02 * a20) * inv;
  m[6] = (a02 * a10 - a00 * a12) * inv;
  m[8] = c02 * inv;
  m[9] = (a01 * a20 - a00 * a21) * inv;
  m[10] = (a00 * a11 - a01 * a10) * inv;
  m[15] = 1;
  return m;
}
```

取数方向注意一下：`a01` 取的是 `model[4]`，行列主序的又一次现场练习——伴随矩阵公式按数学记号写下标，代码按列主序翻译。det 兜底 `|| 1` 防止退化矩阵除零。着色器侧用它变换法线时 w 取 0，让平移量失效。

### 片元着色器：双光源循环

```wgsl
@fragment
fn fs(v: VertexOut) -> @location(0) vec4f {
  // 插值会改变向量长度：法线必须逐片元重新归一化，否则高光会拉丝
  let n = normalize(v.normal);
  let viewDir = normalize(frame.cameraPos.xyz - v.worldPos);

  // 双光源累加：漫反射 + 高光一起算（Blinn-Phong 公式见 GAMES101 笔记 5.1）
  var lightColors = array<vec3f, 2>(WARM, COOL); // 动态索引的本地数组必须 var
  var diffuse = vec3f(0.0);
  var specular = vec3f(0.0);
  for (var i = 0; i < 2; i++) {
    let lp = frame.lights[i];
    let toLight = lp.xyz - v.worldPos;
    let dist = length(toLight);
    let L = toLight / dist;
    let H = normalize(L + viewDir); // 半程向量：Blinn 对 Phong 的改进
    let atten = lp.w / (1.0 + 0.09 * dist * dist); // 平方反比的数值稳定版
    let ndl = max(dot(n, L), 0.0);
    diffuse += lightColors[i] * ndl * atten;
    specular += lightColors[i] * pow(max(dot(n, H), 0.0), 90.0) * atten;
  }
```

第一行的 `normalize` 是本模块第一个高频坑：插值保方向不保长度，直接拿插值法线点积，高光会拉丝。衰减项写成 `I / (1 + k·r²)` 而非裸的 `I / r²`——分母加 1 让光源近处不发散，是平方反比的数值稳定版。`pow` 前必须 `max(dot, 0.0)`：负底数配分数指数在浮点里未定义，会得到 NaN 黑块。循环里那个 `var lightColors` 也有讲究：WGSL 规定动态索引的本地数组必须用 `var` 声明，`let` 过不了编译。

材质分支之后（立方体的石墨灰 kd、地面的格点与远处淡出）就到 gamma 出口，前文已示。

### 鼠标驱动光源与双管线

鼠标的 NDC 坐标被折算成一段绕立方体的弧：横向滑动改变方位角，纵向改变高度，目标位置再经过低通插值成为实际光源——灯是「飘」过去的，手感带阻尼。光源自己也要可见：demo 复用立方体几何，配第二条只换片元入口的管线渲染一个自发光小立方体当标记。

```ts
const markerPipeline = device.createRenderPipeline({
  layout: 'auto',
  vertex: { module, entryPoint: 'vs', buffers: [vertexLayout] }, // 同一顶点入口
  fragment: { module, entryPoint: 'fsMarker', targets: [{ format }] },
  primitive: { topology: 'triangle-list', cullMode: 'none' }, // 标记小到无需剔除
  depthStencil,
});
```

双管线共享顶点着色器与缓冲，`fsMarker` 输出随时间微闪的暖色——它自己是光源，不需要被照亮，也就不进光照循环。这套「一几何多管线」的手法在 2.5 的程序化几何与 Day 3 的后处理里都会反复出现。

## 常见坑

| 报错/症状 | 原因 |
|-----------|------|
| （无报错）高光拉丝、明暗斑驳 | 法线插值后没逐片元 `normalize`，长度漂移改变了点积 |
| （无报错）非均匀缩放后光照错乱 | 拿 model 当法线矩阵，法线被缩放掰歪；换 `mat4NormalFromModel` |
| （无报错）高光处白块或黑块爆掉 | `pow` 前没 `max(dot, 0.0)`，负底数未定义 |
| 第二个光源颜色串位、亮度异常 | `array<vec3f, N>` 按 16 字节步进而 JS 按 12 字节打包；改 `array<vec4f, N>` |
| `array must be var` 类编译错误 | 动态索引的本地数组用了 `let` 声明 |
| 画面整体发闷偏暗 | 忘了 gamma：线性空间的颜色直接输出，被显示器的 2.2 曲线压暗；出口补 `pow(color, 1/2.2)` |
| 画面整体发灰过亮 | 纹理资产本身是 sRGB 编码，又被手动做了一次 gamma 修正（双重编码） |
