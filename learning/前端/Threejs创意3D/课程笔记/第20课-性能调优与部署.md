## 🎯 核心概念

### 1. Draw Call

Draw Call = CPU 向 GPU 发送一次渲染指令。

**类比**：餐厅点餐——你每点一个菜，服务员就跑一次厨房（Draw Call）。如果你点了 100 个菜，服务员要跑 100 次，很慢。更好的做法是把 100 个菜写在一张单子上，服务员只跑一次（InstancedMesh）。

**为什么 Draw Call 是瓶颈？**
- 每次 Draw Call，CPU 需要：设置渲染状态（材质/纹理/混合模式）→ 发送顶点数据 → 通知 GPU 绘制
- 这些"状态切换"有固定开销，GPU 本身画得很快，但 CPU 准备数据慢
- 典型瓶颈：1000+ Draw Call 时 CPU 帧率开始下降

### 2. InstancedMesh

一次 Draw Call 渲染成千上万个**相同几何体**的实例。

```typescript
const mesh = new THREE.InstancedMesh(geometry, material, 1000)
for (let i = 0; i < 1000; i++) {
  dummy.position.set(...)
  dummy.updateMatrix()
  mesh.setMatrixAt(i, dummy.matrix)  // 每个实例独立变换
  mesh.setColorAt(i, color)          // 每个实例独立颜色
}
```

**对比**：

| | 普通 Mesh × 1000 | InstancedMesh × 1000 |
|--|--|--|
| Draw Call | 1000 | 1 |
| GPU 内存 | 1000 份几何体 | 1 份几何体 |
| 独立控制 | ✅ 完全独立 | ✅ 位置/颜色/缩放 |
| 适用 | 不同物体 | 相同物体的不同实例 |

### 3. 性能监控

```typescript
const info = renderer.info
// info.render.calls    → Draw Call 数量
// info.render.triangles → 三角形数量
// info.memory.geometries → 几何体数量
// info.memory.textures   → 纹理数量
```

### 4. 优化策略汇总

| 策略 | 方法 | 效果 |
|------|------|------|
| 减少 Draw Call | InstancedMesh / 合并几何体 | ↓ CPU 开销 |
| 纹理压缩 | KTX2 / Basis / WebP | ↓ 显存 ↓ 加载 |
| LOD | 远处低面数模型 | ↓ 三角形 |
| Shader 优化 | 减少分支/采样 | ↓ GPU 时间 |
| Tree-shaking | Vite 自动移除未用代码 | ↓ 包体积 |

### 5. 移动端 3 大性能要点

1. **Draw Call < 200**：移动端 CPU 更弱
2. **纹理尺寸 < 1024**：移动端显存有限
3. **Shader 简单**：移动端 GPU 算力低

## 🚀 部署

最后一课的收官环节：优化到 60fps，然后部署上线。

### 构建与产物

```bash
pnpm build   # 产物输出到 dist/
pnpm preview # 本地预览构建产物
```

`dist/` 里是纯静态文件，扔到任何静态托管上就能跑。

### base: './'（相对路径）

`vite.config.ts` 里配了 `base: './'`，所有资源引用都变成相对路径，产物放到**任意静态目录**（包括子路径）都能跑。

**类比**：base 路径就像搬家后的门牌号前缀。写死 `/assets/main.js` 相当于邀请函上只写「三楼左转」——客人必须从你所在小区的大门（域名根）进来才找得到；写 `./assets/main.js` 相当于写「从当前位置三楼左转」——客人从哪条路来都能找到。

| base | 资源引用 | 适用 |
|------|---------|------|
| `'/'`（默认） | `/assets/main.js` | 只部署在域名根 |
| `'./'`（本项目） | `./assets/main.js` | 根路径 / 子路径 / GitHub Pages 项目页 |
| `'/my-app/'` | `/my-app/assets/main.js` | 固定子路径 |

本项目用 hash 路由（`#lesson-17`），路由不占 URL 路径段，`base: './'` 是最省心的选择。

### 分包（manualChunks）

```typescript
manualChunks(id: string) {
  if (id.includes('gsap')) return 'gsap'
  if (id.includes('node_modules') && id.includes('three')) return 'three'
},
```

**类比**：就像图书馆分区——工具书（three、gsap）放在固定架位，从不挪动；新到的小说（你的课程代码）随便换，读者手里的工具书借书卡（浏览器缓存）永远有效。

构建后每课各自一个 `main-*.js` 懒加载 chunk（`import.meta.glob` 动态导入的功劳），首屏只加载入口 + 选中的那一课。gsap chunk 约 750KB（gzip 约 207KB），是全量插件的体积，属于预期。

注意：Vite 8（rolldown）的 `manualChunks` 只接受函数形式，不接受对象形式。

### Draco 解码器路径（已知问题）

`DRACOLoader` 按 `setDecoderPath()` 给的路径去 fetch 解码器文件。项目里两处写法都有坑：

- `lessons/08` 写的 `'three/examples/jsm/libs/draco/'`：这只是个普通字符串，Vite 不会据此拷贝文件，运行时 fetch 不到。当前演示模型都不是 Draco 压缩的，解码器从未被真正请求，所以问题没暴露。
- `homework/08` 写的 `'/draco/'`（public/ 下确实有文件）：dev 和根路径部署没问题，但子路径部署时 `/draco/` 会指向域名根，404。

正确写法：`dracoLoader.setDecoderPath('./draco/')`——public/draco/ 构建时原样拷到 dist/draco/，相对路径在根路径和子路径部署下都成立。

### 静态托管三平台

Vercel / Netlify / GitHub Pages 都是「导入 Git 仓库 → 构建命令 `npm run build` → 输出目录 `dist`」三步走。Vercel 和 Netlify 选 Vite preset 自动识别；GitHub Pages 用官方 deploy-pages 工作流，项目页是子路径，`base: './'` 已兼容。

### 体积预算

- 单页首屏（HTML + JS + CSS）：< 500KB（gzip 后）
- 全页资源（含模型纹理）：< 5MB
- 单张纹理：≤ 1024×1024，能压缩用 KTX2/WebP
- 单个模型：< 2MB，用 Draco 压缩

public/ 下的 room 场景资源较大（全产物约 50MB），只有第 08 课按需加载，不影响其他课首屏；要给移动端用户部署时优先压缩这批。

## 费曼学习法

**概念：Draw Call**

**AI 用大白话讲**：
> 想象你在一个餐厅，点了 100 道菜。如果服务员每道菜都跑一次厨房（100 个 Draw Call），那服务员会累死（CPU 瓶颈），即使厨师做得很快（GPU 快）。
>
> 更好的做法：你把 100 道菜写在一张菜单上，服务员只跑一次厨房（1 个 Draw Call = InstancedMesh）。厨师看到菜单后，一次性把所有菜做好。
>
> 但有个限制：菜单上的菜必须是同一种类型（相同几何体）。如果你点了 100 种不同的菜（不同材质），那就没办法合并成一张菜单了。
