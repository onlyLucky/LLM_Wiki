## 🎯 核心概念

### 1. 多场景管理架构

每个场景是独立的 `Scene3D` 对象，包含独立的 Scene、Camera、update 和 dispose。

```typescript
interface Scene3D {
  scene: THREE.Scene
  camera: THREE.PerspectiveCamera
  update: (time: number) => void
  dispose: () => void
}
```

**类比**：电视频道——每个频道有自己的节目（场景），遥控器（管理器）负责切换。切换时旧频道停止播放，新频道开始播放。

### 2. 场景切换过渡（淡入淡出）

用一个黑色 DOM overlay 覆盖 canvas，通过 opacity 实现淡入淡出。

```typescript
overlay.style.opacity = '1'  // 淡出（黑色覆盖）
await sleep(500)
currentScene = newScene       // 切换
overlay.style.opacity = '0'  // 淡入（露出新场景）
```

### 3. dispose 防止内存泄漏

Three.js 不会自动释放 GPU 资源，必须手动 dispose。

**需要释放的资源**：
| 资源 | 释放方法 | 忘记释放的后果 |
|------|----------|---------------|
| 几何体 | `geometry.dispose()` | GPU 顶点缓冲区泄漏 |
| 材质 | `material.dispose()` | Shader 程序泄漏 |
| 纹理 | `texture.dispose()` | GPU 纹理内存泄漏 |
| 渲染目标 | `renderTarget.dispose()` | 帧缓冲区泄漏 |

**关键认知：`scene.remove()` 不等于 `dispose()`**。remove 只让对象不参与渲染，GPU 侧的顶点缓冲区并不会回收——切几次场景就泄漏几次。

**怎么验证资源真的被释放？用 `renderer.info.memory`**：

```typescript
const before = { ...renderer.info.memory }
oldScene.dispose()
const after = renderer.info.memory
console.log(`geometries: ${before.geometries} -> ${after.geometries}, textures: ${before.textures} -> ${after.textures}`)
```

两个容易踩的坑：
- 几何体**首帧渲染后**才计入计数（GPU buffer 是懒上传的），刚创建还没渲染的资源不在计数里
- dispose 的递减是**同步**的，dispose 前后各打印一次就能看到计数回落

### 4. 预加载 vs 按需加载

| | 预加载 | 按需加载 |
|--|--|--|
| 首次加载 | 慢（加载所有） | 快（只加载当前） |
| 切换体验 | 快（已缓存） | 慢（需等待） |
| 带宽 | 高（可能浪费） | 低（按需） |
| 适用 | 小项目、资源少 | 大项目、资源多 |

**50MB × 5 页面的例子**：
- 预加载：首次加载 250MB（浪费 150MB）
- 按需加载：只加载访问的 100MB

本课落地「按需加载」：管理器注册的是场景**工厂函数**（怎么造），切换到它时才创建实例；切换时销毁旧场景。用 LoadingScreen 过渡页掩盖创建耗时。

### 5. hash 路由：手写一遍就懂 React Router

hash 路由只有两个要素：读 `location.hash` + 监听 `hashchange`。浏览器的前进/后退按钮同样会触发 hashchange，所以路由天然免费获得历史记录与「分享链接」能力。

```typescript
/** 路由表：地址 ↔ 场景 */
const ROUTE_TO_SCENE = {
  'scene-a': 'geometry',
  'scene-b': 'particles',
  'scene-c': 'shader',
}

window.addEventListener('hashchange', applyRoute)   // 听：前进/后退也走这里

function applyRoute() {
  const route = location.hash.replace('#', '') || 'scene-a'   // 读
  const sceneName = ROUTE_TO_SCENE[route] ?? 'geometry'
  if (sceneName !== store.getState().currentScene) {
    store.setState({ currentScene: sceneName })
  }
}
```

**与 React Router 的对应关系**——在 React 里，把 SceneManager 挂进 useEffect 生命周期：

```tsx
function App() {
  const { scene } = useParams()                      // React Router 提供
  const managerRef = useRef<SceneManagerMulti | null>(null)

  useEffect(() => {
    const manager = new SceneManagerMulti(renderer)
    // ... 注册场景工厂
    managerRef.current = manager
    return () => manager.destroy()                   // 组件卸载 = 销毁全部资源
  }, [])

  useEffect(() => {
    managerRef.current?.switchScene(scene)           // 路由变化 = 切场景
  }, [scene])

  return <canvas />
}
```

| 本课手写 | React Router 对应 |
|----------|-------------------|
| 读 `location.hash` 解析路由 | `useParams()` / `useSearchParams()` |
| `hashchange` 监听 | 路由状态变化 → 组件重渲染 |
| `location.hash = route` 写地址 | `navigate('/scene-b')` |

两个 useEffect 的分工：第一个管「生与死」（挂载创建、卸载销毁，只跑一次），第二个管「路由响应」（参数一变就切场景）。

### 6. 30 行发布订阅 store —— 这就是 Zustand 的核心思想

问题：状态散在各闭包里，下拉框要通知管理器、管理器要通知 UI、路由还要通知两者——改一处牵三处。

解法：**单一数据源 + 订阅更新**，30 行以内：

```typescript
function createPubSubStore<T extends object>(initialState: T) {
  let state = initialState
  const listeners = new Set<(state: T, prevState: T) => void>()

  return {
    getState: () => state,
    setState(partial: Partial<T>) {
      const prevState = state
      state = { ...state, ...partial }
      listeners.forEach((listener) => listener(state, prevState))
    },
    subscribe(listener: (state: T, prevState: T) => void) {
      listeners.add(listener)
      return () => { listeners.delete(listener) }    // 取消订阅，防泄漏
    },
  }
}
```

Zustand 额外提供的只是 React 绑定（`useStore` 内部用 `useSyncExternalStore`）、中间件与 immer 糖——核心思想与上面完全一样。

**单一数据流原则：任何入口只改状态源，不直接调用彼此。**

```
下拉框 onChange ────┐
                    ├──> 只改 hash / store ──> 订阅者响应：
地址栏 / 前进后退 ───┘       1. 同步地址栏  2. 同步下拉框  3. manager.switchScene()
```

类比：store 是中央调度台，下拉框、地址栏、场景管理器都只对调度台说话，互相之间不串线。防死循环的两个关键：
- 写回 hash 前先判断值是否已一致（一致就跳过，不再触发 hashchange）
- 反向同步 UI 用不触发 onChange 的 `panel.setValue()`

## 💻 代码实现要点

### 1. SceneManagerMulti 类（按需加载版）

注册的是场景**工厂函数**，切换到它时才创建实例。切换走完整流程：

```
遮罩变黑 (0.5s) → dispose 旧场景 + renderer.info.memory 前后打印
              → Loading 页进度 (4 × 120ms) → 工厂创建新场景
              → Loading 隐藏 + 遮罩淡入 (0.5s)
```

- 过渡锁 `transitioning`：防止过渡中被再次触发（重复调用会被直接吞掉）
- 销毁旧场景后从实例表删除——下次切回来会重新创建，这是按需模式的代价；收益是内存占用恒定，不会随访问过的场景数增长

### 2. 三个场景（工厂函数）

- 几何体场景：Box + Sphere + Torus 旋转
- 粒子场景：10000 个星空粒子
- Shader 场景：波纹效果全屏 Shader

每个场景的 dispose 逐个释放自己的 geometry/material。销毁是否彻底，切一次场景看控制台的 `[dispose]` 日志就知道。

### 3. 窗口自适应

实例表里只剩活跃场景，resize 只更新它的相机；新场景创建时用当时的窗口尺寸建相机，天然适配。

### 4. 双向同步与防死循环

- 下拉框 onChange → 只写 `location.hash`（不直接切场景，切换由路由统一驱动）
- `hashchange` → applyRoute → store → 订阅者依次做三件事：同步地址栏（值已一致则跳过）、`panel.setValue` 同步下拉框（不触发 onChange）、`manager.switchScene`
- 首次进入：手动读一次路由 + 把初始路由写进地址栏，首屏也走完整 Loading 流程
