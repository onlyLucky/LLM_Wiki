# 3.1 ShaderMaterial：把两天的 shader 装进工程框架

> Day 3 · 模块 1 · 约 55 分钟
> 理论对照：《Threejs创意3D》第 3 课「材质系统」（[第3课-材质系统.md](../../../Threejs创意3D/课程笔记/第3课-材质系统.md)）——材质体系的系统性讲解在那边；《WebGPU 三天实战课程》3.1「WebGPURenderer 架构与迁移策略」（[3.1-WebGPURenderer架构与迁移策略.md](../../../webgpu/讲义/day3-Three.js桥接/3.1-WebGPURenderer架构与迁移策略.md)）——同一件事在两代渲染器上的做法

手写 WebGL2 你已经能打 90 分：编译链接、VAO 接线、uniform 上传、帧循环，全是你自己敲的。但真实项目没有人为你维护那 150 行脚手架——没人会手写 `createProgram`，就像没人会手写 `addEventListener` 之前先写 DOM 树。Three.js 就是那层「工业化的 chrome.ts」：你在 Day 1 写的每个仪式，它都有对应的现成版本。好消息是两天的 GLSL 一行不用重学——要学的只是「怎么把你的着色器递进去」。

## 为什么迁移：Three.js 帮你写掉的 150 行

对照表先上，你昨天写的每一段都能在右边找到雇主：

| 你 Day 1 手写的 | Three.js 的现成版本 | 省下的 |
|---------------|--------------------|--------|
| `initGL`（context 获取与失败提示） | `new THREE.WebGLRenderer({ antialias: true })` | 20 行 |
| VAO + VBO + vertexAttribPointer 三件套 | `new THREE.PlaneGeometry(2, 2)` | 25 行 |
| `createProgram`（编译链接错误面板） | `new THREE.ShaderMaterial({...})` | 60 行 |
| uniform location 查询 | `uniforms: { u_time: { value: 0 } }` 声明即注册 | 每个少 1 行 |
| 帧循环 + viewport + clear + draw | `renderer.render(scene, camera)` | 20 行 |
| resize 处理与 DPR | `renderer.setSize` + `setPixelRatio` | 15 行 |

**你昨天写的脚手架就是 Three.js 的源代码级缩微版**——这不是巧合，是刻意安排的学习顺序：先手写一遍知道它在帮你干什么，再交出去知道交出去的是什么。webgpu 课的 3.1 讲过同一条迁移曲线（原生 WebGPU → WebGPURenderer），你此刻的既视感完全正确。

## ShaderMaterial 最小闭环

五件套搭起来，一个会呼吸的全屏平面：

```ts
import * as THREE from 'three';
import './style.css';

// 1. 渲染器：WebGL2 context + 尺寸 + DPR 上限
const renderer = new THREE.WebGLRenderer({ antialias: true });
renderer.setSize(innerWidth, innerHeight);
renderer.setPixelRatio(Math.min(devicePixelRatio, 2)); // 总纲性能红线
document.body.appendChild(renderer.domElement);

// 2. 场景与相机：正交相机拍全屏平面（2D 语义）
const scene = new THREE.Scene();
const camera = new THREE.OrthographicCamera(-1, 1, 1, -1, 0, 1);

// 3. 几何：PlaneGeometry 就是你的全屏四边形（默认带 position + uv）
const geometry = new THREE.PlaneGeometry(2, 2);

// 4. 材质：两天的 shader 从这里递进去
const material = new THREE.ShaderMaterial({
  vertexShader: `...`,
  fragmentShader: `...`,
  uniforms: {
    u_time: { value: 0 },
    u_resolution: { value: new THREE.Vector2(innerWidth, innerHeight) },
  },
});

// 5. 网格与渲染循环
scene.add(new THREE.Mesh(geometry, material));
renderer.setAnimationLoop(() => {
  material.uniforms.u_time.value = (performance.now() / 1000) % 3600; // 秒，讲义 1.6 约定；% 3600 防 float 尾数耗尽
  renderer.render(scene, camera);
});
```

顶点着色器里有一个**必须**写的矩阵乘法——这不是选配：

```glsl
// ShaderMaterial 版 vertexShader（注意：不写 #version，见下节）
varying vec2 v_uv;

void main() {
  v_uv = uv; // 内置 attribute，直接读
  // 内置矩阵链：three 每帧更新值，你只负责乘
  gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
}
```

## 内置注入：你免费拿到的 uniform 和 attribute

ShaderMaterial 编译前会替你注入一批声明——你不写，它们也在：

| 注入项 | 类型 | 来自哪里 | 用途 |
|-------|------|---------|------|
| `projectionMatrix` | mat4 | 相机 | 顶点 → 裁剪空间 |
| `modelViewMatrix` | mat4 | 网格×相机 | 模型变换 + 视图 |
| `normalMatrix` | mat3 | 模型 | 法线方向 |
| `cameraPosition` | vec3 | 相机 | 视线 / 高光计算 |
| `modelMatrix` | mat4 | 网格 | 模型变换（拆开用的场合少，用到别自己声明） |
| `viewMatrix` | mat4 | 相机 | 视图矩阵（同上） |
| `position` | vec3 | 几何 | 顶点位置 |
| `normal` | vec3 | 几何 | 顶点法线 |
| `uv` | vec2 | 几何 | 顶点 UV 0–1 |

映射全表看这张图：

![Three.js 内置注入映射图：左面板天青描边列出四个自动注入的 uniform（projectionMatrix mat4 裁剪空间投影、modelViewMatrix mat4 模型乘视图、normalMatrix mat3 法线旋转、cameraPosition vec3 相机世界位），说明文字「不进你的 uniforms 对象、渲染器每帧更新」，底部琥珀色公式「gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0)」；右面板玫红描边列出三个自动注入的 attribute（position vec3 几何顶点位、normal vec3 顶点法线、uv vec2 顶点 UV 0–1），说明 ShaderMaterial 为 GLSL1 风格转译（attribute/varying 关键字直接用、不写 #version），底部琥珀色提示「varying vec2 v_uv; v_uv = uv;」；下半部深色卡为自定义 uniform 的 TS 声明与每帧写值对照原生 uniform1f 的写法，并列三个易忘点（v_uv 要自己 varying 一遍、u_mouse 记得 y 翻转、DPR 取 min(devicePixelRatio, 2)）；底部通栏警示第一次迁移最常见的失败：以为 uv 免费就忘了 varying——attribute 只活在顶点着色器，片元要接还得交接](../../assets/diagrams/threejs-uniform-mapping.svg)

对着图最该盯住的是右下的琥珀行：**`v_uv` 还是要自己 varying 一遍**——`uv` 这个 attribute 只活在顶点着色器，片元想用它，交接仪式（1.5 的接头暗号）一样要走。这是第一次迁移的最高频失败点：以为「内置」等于「到处都在」，fragment 里直接写 `uv`——three 没有注入 vec2 varying uv，编译器直接报 undeclared identifier（另一种「编译能过但读到 0」的坑是：varying 声明了、顶点忘了赋值——两种死法排查方向不同）。

RawShaderMaterial 与 ShaderMaterial 的分界：前者什么都不注入（你的 Day 1 原味），后者送全套内置。**课程约定：用 ShaderMaterial**——工业项目的 95% 场景它都够，需要 Raw 的时刻你会知道的。

## 3.1 版 GLSL 风格差异（硬约束，先背表）

两天养成的 GLSL 习惯里，有两个要为 Three.js 改口——这是规格级的约定，违反就编译失败或行为错乱：

| 事项 | 原生 WebGL2（Day 1–2） | ShaderMaterial（Day 3） |
|------|----------------------|------------------------|
| `#version 300 es` | 着色器第一行必写 | **不写**——three 自动注入版本与前缀 |
| attribute / in | `in`（ES 3.00 风格） | `attribute` / `varying`（GLSL1 关键字，three 转译升级） |
| `out vec4 fragColor` | 必须自声明 | **不写**——用内置的 `gl_FragColor` |
| `texture(u, uv)` | ES 3.00 函数 | `texture2D(u, uv)`（GLSL1 名，转译后等价） |
| precision | fragment 顶部手写 | three 前缀已含（highp） |

课程文件组织同步调整：Day 3 的着色器仍放 `shaders/` 子目录、仍 `?raw` 导入，但源码内不写 `#version`、输出用 `gl_FragColor`、采样用 `texture2D`。**两套风格分属两个世界，别混着抄**——从 Day 2 的 fragment 里复制函数体（纯算法部分）没问题，头部五件（version / precision / out / in / texture）要按本表换。

## uniform 的 TS 侧管理

原生时代你查 location、每帧 `uniform1f`；ShaderMaterial 把 location 藏起来，你只碰 `value`：

```ts
const material = new THREE.ShaderMaterial({
  uniforms: {
    u_time: { value: 0 },
    u_mouse: { value: new THREE.Vector2(0.5, 0.5) }, // vec2 用 Vector2
    u_colorA: { value: new THREE.Color('#FF4D6D') }, // 颜色用 Color
  },
  // ...
});

// 帧循环里只写 value——location 的活 three 全包
material.uniforms.u_time.value = t;
material.uniforms.u_mouse.value.set(mx, my);
```

与原生的对照：`uniform1f(uTime, t)` ↔ `uniforms.u_time.value = t`；`uniform2f(uMouse, x, y)` ↔ `uniforms.u_mouse.value.set(x, y)`——语义完全同构，只是从「命令式上传」变成「改对象属性」，React 出身的你对后者天然亲切。

`u_mouse` 迁移时两个 Day 1 的老坑回来：**DPR**（shader 里要的分辨率是 CSS 像素还是物理像素，选一个口径并全链路一致）与 **y 翻转**（DOM 事件的 y 向下、UV 的 y 向上——自己接事件桥时翻转别忘了；课程骨架在 Day 3 的 main.ts 里统一处理）。

## 什么时候根本不该迁移

迁移不是信仰，是选型。判断标准只有一个问题：**有没有 3D 物体**。

| 效果类型 | 选型 | 理由 |
|---------|------|------|
| 纯 fragment 全屏背景（Day 2 云海、voronoi、调色板） | 原生 WebGL2 更轻 | 没有 3D 物体就没有 Three.js 的理由——一个四边形不值得引入 600KB |
| 混合 DOM 与 3D（图卡失真、粒子 hero、滚动场景） | Three.js | 需要场景图、射线拾取、纹理管理——原生日志会长到失控 |
| 需要生态（GLTF 加载、后期链、R3F 组件） | Three.js | 生态不是自己写的理由，是站在上面的理由 |

「没有 3D 物体就没有 Three.js 的理由」——Day 2 的云海背景建议原样留在原生工程里（本课的 Day 2 demo 就是这个判断的示范）；Day 3 的图卡、粒子、后期才有迁移的全部收益。这个判断题在面试和真实项目里都会反复出现，现在就把它写进你的工程直觉。

## How：demo 01「ShaderMaterial 初见」逐段精讲

demo 01 把 Day 2 作业 B 的全息卡面搬进 ShaderMaterial——同一张卡面，两个世界，并排对账。真实工程版 41 行，主体如下：

```ts
// demo 01 的主体（Day 2 作业 B 全息卡面的 Three.js 版，41 行 vs 原生 87 行）
import * as THREE from 'three';
import { createChrome } from '../../../shared/chrome.ts';
import vsSource from './shaders/vertex.glsl?raw'; // ?raw 只有默认导出——01-环境准备的同一约定
import fsSource from './shaders/fragment.glsl?raw';

// 五件套之三：场景 + 正交相机（正交 + 全屏平面 = three 版「全屏四边形」）
const scene = new THREE.Scene();
const camera = new THREE.OrthographicCamera(-1, 1, 1, -1, 0, 1);
const material = new THREE.ShaderMaterial({
  vertexShader: vsSource, fragmentShader: fsSource, // 卡面 fragment 按 3.1 风格表换口后原样复用
  uniforms: {
    u_time: { value: 0 },
    u_resolution: { value: new THREE.Vector2(1, 1) },
    u_parallax: { value: new THREE.Vector2(0, 0) }, // 视差偏移，TS 侧 lerp 后写入
  },
});
scene.add(new THREE.Mesh(new THREE.PlaneGeometry(2, 2), material)); // 五件套之四：网格

// resize 时序：chrome 的首次 applySize 早于 renderer 创建，守卫必须先行
let renderer: THREE.WebGLRenderer | null = null;
function syncSize(w: number, h: number) {
  if (!renderer) return;
  renderer.setSize(w, h, false); material.uniforms.u_resolution.value.set(w, h); // 物理像素直写
}

const chrome = createChrome({ /* DOM 外壳：canvas 由它创建并已设为物理像素 */ });
renderer = new THREE.WebGLRenderer({ canvas: chrome.canvas, antialias: true }); // 渲染权交接
renderer.setPixelRatio(1); syncSize(chrome.width, chrome.height);

// 帧循环：视差 lerp + 三项 uniform 写入，渲染只剩一行
const start = performance.now();
let px = 0, py = 0;
chrome.startLoop((now) => {
  px += ((chrome.pointer.sx - 0.5) * 0.06 - px) * 0.08; // 视差 3% + lerp 0.08（awwwards 手感默认档）
  py += ((chrome.pointer.sy - 0.5) * 0.06 - py) * 0.08;
  material.uniforms.u_time.value = ((now - start) / 1000) % 3600; // 毫秒转秒（契约）；% 3600 防 float 尾数耗尽
  material.uniforms.u_parallax.value.set(px, py);
  renderer!.render(scene, camera);
});
```

值得盯住的是行数对账：**原生 87 行 → three 极简版 34 行 → 本工程 41 行**——极简版省掉的 53 行全是「仪式」（初始化、几何接线、编译、帧循环管理），一行算法都没省：卡面的 SDF、fwidth 抗锯齿、呼吸参数化原样复用。这就是「脚手架交出去、算法留下来」的定量账本。工程版比极简版多出的 7 行也不是算法，是两个真实项目的必修课：其一，**渲染权交接**——画布由 chrome 创建并已设为物理像素，three 用 `WebGLRenderer({ canvas })` 接管它，`setPixelRatio(1)` + `setSize(w, h, false)` 表示「尺寸你别再动，只管画」；其二，**syncSize 守卫**——chrome 的首次 applySize 早于 renderer 创建，没有 `if (!renderer) return` 就是开局一次 undefined 报错（README 的常见报错表第一条）。视差（`u_parallax` 驱动卡面 ±3% lerp 偏移）是唯一的算法增量——输入直接读 `chrome.pointer` 的平滑坐标（y 翻转与 0.08 阻尼都在 shared/chrome.ts 里），1.7 的事件桥整段外包给了 chrome。

## 常见坑

| 症状 | 原因 |
|------|------|
| 画面全黑 | vertexShader 忘写 `projectionMatrix * modelViewMatrix` 乘法——顶点没进裁剪空间，图元被裁掉 |
| fragment 里直接写 uv，编译报 undeclared identifier | `uv` 是 attribute 只活在顶点着色器；片元要 `varying vec2 v_uv` 交接一遍（本讲头号坑） |
| 编译报错「cannot use in/out」之类 | 着色器里写了 `#version 300 es` 或 `in`/`out` 关键字——ShaderMaterial 是 GLSL1 风格转译，按 3.1 风格表换口 |
| fragment 输出没反应 | 还在写 `out vec4 fragColor`——three 的转译路里输出变量名是 `gl_FragColor`，声明也不用你写 |
| 鼠标交互上下颠倒 | DOM 的 y 向下、UV 的 y 向上——事件桥里翻转（1.5 常见坑表第 4 行的三度登台） |
| 画面在高分屏糊成一团 | DPR 没设：`renderer.setPixelRatio(Math.min(devicePixelRatio, 2))`——上限 2 是性能红线不是建议 |
