# 1.7 交互输入：从鼠标到滚动——awwwards 手感的工程学

> Day 1 · 模块 7 · 约 60 分钟
> 理论对照：无直接章节——webgpu 课的鼠标 uniform 是本篇的极简版；本篇是该知识点的完整展开，也是本课「交互支柱」的地基

同一个 shader，鼠标跟不跟随、跟得顺不顺滑，是 demo 级与 awwwards 级的分水岭。打开 lusion.co，光标后面那枚光晕永远慢半拍地追着你，按住时画面像被捏了一下——这些手感背后没有魔法，只有一条把浏览器事件翻译成 uniform 的流水线。这一讲把这条流水线的完整工程讲透：事件怎么收、状态怎么存、坐标怎么换、动画怎么弹。从此交互对你是一个「模式」，而不是每次现想的「技巧」。

## 事件桥：浏览器世界与 GPU 世界的翻译官

交互的第一性原理是**事件与渲染必须解耦**，事件桥就是那个解耦层。它一头站在 DOM 世界听事件，一头站在 GPU 世界供数据，中间用一个 JS 状态对象把两个节拍不同的世界隔开。整条链路长这样：

![事件桥全链路图：标题「事件桥：浏览器世界 → GPU 世界的翻译官」，副标题金句「事件更新状态，帧循环消费状态」。主体是五个圆角节点从左到右用玫红箭头串联——环节一「浏览器事件（DOM 世界）：pointermove / down、wheel · click · touch」；环节二「chrome.pointer（JS 状态对象）：x/y · sx/sy · isDown、wheel · clickTime」，该节点下方用琥珀色虚线挂着一个「lerp 平滑（内建）：sx += (x - sx) * 0.08」的子框；环节三「uniform 写入（每帧 · 帧循环内）：uniform2f(u_mouse, chrome.pointer.sx)」；环节四「shader 响应（GPU 世界）：距离场 · 波包、视差 · 流动」；环节五「画面：60 fps 连续帧」。环节一下方有琥珀色警示「事件频率 ≠ 帧率／回调里直接画 = 掉帧根源」；环节三下方标注「rAF 里读，不在回调里画／事件只改状态，渲染交给帧循环」。底部玫红大字「事件更新状态，帧循环消费状态」，注释一行「这句话就是整个模式——记住它，之后所有交互 demo 都是它的变奏」](../../assets/diagrams/interaction-event-bridge.svg)

对着图从左到右过一遍数据流：浏览器事件（pointermove、pointerdown/up、wheel、click、touch）到达时，回调只做一件事——把值写进 `chrome.pointer` 这个状态对象；帧循环每帧从这里读出最新状态（含 lerp 平滑后的坐标），写进 uniform；shader 拿到 uniform 后用距离场、波包这些你 Day 1 已经认识的工具做出响应；画面以 60 fps 连续输出。图里最值得盯住的一条线：**箭头跨过「chrome.pointer」这道墙的只有一次写入和一次读取**——事件世界和渲染世界再无别的接触点。

为什么不在事件回调里直接 draw？两个理由，每一个都足够致命：

| 理由 | 展开 |
|------|------|
| 事件频率 ≠ 帧率 | 高刷鼠标的 pointermove 每秒能发 125–1000 次，而屏幕只有 60 帧。回调里直接 draw，轻则一帧重复渲染白白烧 GPU，重则把 GPU 队列塞满掉帧——rAF 是唯一正确的渲染节拍器 |
| GPU 无事件概念 | shader 是每帧对全屏像素求值的纯函数，它不知道「事件」这回事，只认 uniform 的当前值。事件想影响画面，唯一通道就是先落进状态、等帧循环来读 |

> **事件更新状态，帧循环消费状态。** 这句话就是整个模式——本篇剩下的所有内容（lerp、坐标域、涟漪、触摸）都只是这句话在不同输入类型上的变奏。

## 五类输入的 uniform 方案表

五类输入对应五个 uniform 方案，之后三天所有交互 demo 都从这张表查起。uniform 的形态设计比事件绑定本身更值得琢磨——它决定了 shader 侧响应段的写法：

| 事件 | JS 状态 | uniform 形态 | 典型效果 |
|------|---------|-------------|---------|
| pointermove | `pointer.sx / sy`（lerp 平滑后） | `vec2 u_mouse` | 视差、光晕跟随 |
| pointerdown / up | `pointer.isDown` | `float u_down` | 按压涟漪、吸附 |
| 拖动（down + move 组合） | isDown 期间坐标的位移增量 | `vec2 u_drag` | 扭曲、惯性 |
| wheel | `pointer.wheel`（累积像素，未 clamp） | `float u_scroll`（归一化累积） | Day 1 demo 06 用「拨动」语义（条纹相位推进），Day 3 换「页面进度」语义 |
| click | `pointer.clickTime / clickX / clickY` | `float u_clickTime` + `vec2 u_clickPos` | 扩散波 |

三处设计决策值得你咀嚼：鼠标用 `vec2` 而不是两个 `float`，这是总纲的 uniform 数量纪律——一个语义一个 uniform，塞不下就打包装进向量；拖动没有专属事件，它是「isDown 为 true 期间」的 move 组合语义，翻译工作在 JS 侧完成，shader 只见结果；wheel 的原始值是累积像素且向下为正、没有上界，归一化到 0–1 是 demo 自己的职责（demo 06 会示范完整做法）。

## lerp 平滑：顺滑感的全部秘密

顺滑感的全部秘密只有一行代码：每帧只向目标走剩余距离的固定比例。

```text
smooth += (raw - smooth) * 0.08
```

三个角色逐个拆解：`smooth` 是当前显示值（你上一帧看到的位置），`raw` 是目标值（鼠标此刻的真实位置），`0.08` 是阻尼系数——每帧只追回剩余差距的 8%。它的数学本质是指数收敛：每帧残差乘以 0.92，所以光晕永远追得上鼠标、又永远慢半拍，这个「慢半拍」正是 awwwards 手感的来源。

系数就是手感旋钮，三档覆盖 90% 的场景：

| 系数 | 手感 | 适用场景 | 60fps 下收敛到 10% 残差 |
|------|------|---------|------------------------|
| 0.04 | 慢丝滑 | 大面积视差背景、氛围层 | 约 0.95 秒（56 帧） |
| 0.08 | 默认档 | 光标跟随、光晕（chrome 默认值） | 约 0.46 秒（28 帧） |
| 0.15 | 跟手 | UI 级元素、需要精确反馈的交互 | 约 0.24 秒（14 帧） |

「CSS transition 之于直接赋值，lerp 之于事件桥」——你在 React 里从不改 state 后手动设 style，你加一道 transition 让浏览器补间；事件桥里 `raw` 就是那次「直接赋值」，lerp 就是那道补间。区别是补间发生在你自己的帧循环里，每一帧都由你亲手算出来。

这套机制 chrome 已经内置，`sx / sy` 就是平滑后的坐标——你只需要读懂它：

```ts
// shared/chrome.ts —— 已内置，每帧由 startLoop 自动执行，读懂即可
const POINTER_LERP = 0.08; // 默认阻尼：60fps 下约 0.5s 收敛（讲义 1.7 的默认档）

// 注意平滑发生在帧循环里，而不是事件回调里——这正是事件桥的纪律
pointer.sx += (pointer.nx - pointer.sx) * POINTER_LERP;
pointer.sy += (pointer.ny - pointer.sy) * POINTER_LERP;
```

一句诚实的简化声明：固定系数对帧率敏感——同样 0.08 在 144 Hz 屏上收敛会明显变快，严谨做法是按 `dt` 把系数换算成帧率无关的形式。课程统一锁定 60 fps 口径、简化为固定系数，Day 3 接 Lenis 平滑滚动时再回收这个话题。

## 坐标域的换算：一次讲清不再糊涂

坐标域是交互 bug 的最大产地，这里一次换算讲清楚，之后三天不再回来。完整链路是三级跳：

```text
e.clientX / clientY        画布内 CSS 像素     （DOM 习惯：左上原点，y 向下增）
  → 减 rect.left / top，再除以画布 CSS 尺寸   → 归一化 0–1
  → 乘 2 减 1                                → 居中域 -1..1（SDF 与图形运算的主场）
```

y 翻转是这条链路上最容易漏的一步：DOM 的 y 向下增，GL 的 y（`gl_FragCoord`）向上增，两边坐标系上下颠倒。漏了翻转，光标向上移动、画面里的光晕向下跑——症状极其特征化。翻转只需一行 `1.0 - y`：

```ts
canvas.addEventListener('pointermove', (e) => {
  const r = canvas.getBoundingClientRect();
  // 除以画布尺寸：CSS 像素 → 0–1；clamp 防止光标拖出画布时值域越界
  const nx = Math.min(Math.max((e.clientX - r.left) / r.width, 0), 1);
  // y 翻转：DOM 向下增，GL 向上增——手写事件时最常漏的一步
  const ny = 1 - Math.min(Math.max((e.clientY - r.top) / r.height, 0), 1);
});
```

宽高比再出镜：0–1 域的 x 轴在宽屏上被拉伸，`length()` 算出来的「圆」其实是椭圆。1.5 讲过 `p.x *= u_aspect` 的修正，交互里它每帧都在参与——光晕是圆、涟漪是圆，只要出现距离计算，aspect 就必须在场。

`chrome.pointer` 已经把这一切替你做好：`nx / ny` 是翻转后的归一化坐标（左下原点），`sx / sy` 在此之上再叠加 lerp 平滑。你手写事件监听时（比如拖动增量），才需要把上面那段翻转代码默写出来。

## 点击涟漪：一个 uniform 的完整动画

涟漪是「一个 uniform 驱动一段完整动画」的最小样本，也是 Day 1 作业 challenge 的核心考点。它只靠 `u_clickTime`（触发时刻）一个关键 uniform，其余全部由时间反推——shader 是无状态的，所以正确的姿势不是存一个「点击发生了」的布尔标记，而是存「点击发生在哪一秒」，让动画进度每帧都能算出来：

```text
elapsed   = u_time - u_clickTime          距点击过去了几秒
progress  = elapsed / DURATION            归一化进度 0 → 1
波包      = sin(progress * PI) * exp(-progress * 2.0)   一次性衰减的鼓包
环半径    = progress * MAX_R              波从落点向外跑
```

波包的两段乘法各有分工：`sin(progress * PI)` 走半个正弦周期，从 0 涨到 1 再回 0，天然「起幅—收幅」；`exp(-progress * 2.0)` 让尾巴指数衰减，波越跑越淡。两者相乘，就是一枚扩散一次、绝不往复的环。完整可运行代码如下：

```glsl
#version 300 es
precision highp float;

uniform vec2 u_resolution;
uniform float u_time;
uniform float u_clickTime; // 最近一次点击时刻（秒）；-1 表示从未点击（chrome 约定）
uniform vec2 u_clickPos;   // 点击落点，归一化 0–1，y 已翻转（chrome.pointer.clickX/Y）

out vec4 fragColor;

const float DURATION = 1.2; // 波纹生命周期（秒）
const float MAX_R = 0.65;   // 最大扩散半径（居中域单位）

void main() {
  vec2 uv = gl_FragCoord.xy / u_resolution;
  // 居中 + 等比：涟漪必须是正圆，x 乘 aspect（讲义 1.5 的修正，交互里每帧在场）
  vec2 p = (uv - u_clickPos) * vec2(u_resolution.x / u_resolution.y, 1.0);

  float glow = 0.0;
  // 守卫：clickTime 初始为 -1，不判断的话第 0 帧会算出一条「从未发生」的幽灵波
  if (u_clickTime >= 0.0) {
    float elapsed = u_time - u_clickTime;
    float progress = elapsed / DURATION;
    // 波包：min 钳住 sin 的半周期，保证波「死透」归零而不出现反向环；
    // exp 衰减让尾巴平滑淡出，连击时旧波自动消散、新波无缝接管
    float wave = sin(min(progress, 1.0) * 3.14159265) * exp(-progress * 2.0);
    // 环：距离场减去当前半径，smoothstep 收出细环边缘
    float ring = smoothstep(0.03, 0.0, abs(length(p) - progress * MAX_R));
    glow = wave * ring;
  }

  vec3 base = vec3(0.043, 0.055, 0.078);  // 画布底色 #0B0E14
  vec3 rose = vec3(1.0, 0.302, 0.427);    // 玫红 #FF4D6D
  vec3 color = base + rose * glow;
  fragColor = vec4(color, 1.0);
}
```

把 `u_clickTime` 换成任何「事件发生时刻」，这套「时刻 → elapsed → progress → 波包」的四步就原样复用——按压回弹、滚动推进都是它的变体。

## 触摸：pointer events 一把抓

触摸不是一套新事件，Pointer Events 把 mouse、touch、pen 统一成一条事件流，你的监听代码一行都不用改。`pointermove` 在手指滑动时照常触发，`pointerdown / up` 对应按下与抬手——上一节写的所有逻辑天然在移动端生效，这是浏览器花十年把三套事件模型合并的成果。

唯一的前置是一道 CSS：

```css
canvas { touch-action: none; } /* 没有它，移动端手势被浏览器判定为页面滚动，pointermove 连续流会被掐断 */
```

`touch-action: none` 告诉浏览器「这块区域的手势归我」：不设的话，手指一动浏览器就接管去做页面滚动或下拉刷新，你会只收到一个 `pointercancel` 而不是连续的 pointermove。课程的 `demo.css` 已替你设好，但你要知道它的存在——脱离课程骨架写页面时，这是移动端黑屏级的第一坑。双指缩放（pinch）涉及两个触点的协同，留到 Day 3 与滚动语义一起处理，今天不展开。

## How：demo 04 / 05 / 06 三连精讲

三个 demo 共享同一座事件桥，差别只在 uniform 的语义——这正是「模式」的意义：骨架不变，换 uniform 就换作品。下面逐个过 fragment 响应段；demo 由批 2 生成，本节的代码段就是它们的实现蓝本，uniform 命名与之完全一致。

### demo 04「光标的追随」

三枚 uniform：`u_mouse`（平滑坐标）、`u_mouse_raw`（原始坐标）、`u_down`（按压因子）。原始与平滑双坐标并传，是拖尾的关键——两者的差就是速度向量，不花一行额外计算。

按压回弹有个值得咀嚼的取舍：`easeOutBack` 需要「按下多久了」这条时间轴，而 shader 是纯函数、记不住状态，所以动画在 JS 侧算好，shader 只消费最终因子——事件桥翻译的不止坐标，还有时间：

```ts
// JS 侧：按压因子沿 0.6s 时长推进，easeOutBack 提供过冲回弹（函数定义见讲义 1.6）
const goal = chrome.pointer.isDown ? 1 : 0;
if (goal !== lastGoal) { pressFrom = press; pressStart = now / 1000; lastGoal = goal; }
const t = Math.min((now / 1000 - pressStart) / 0.6, 1);
press = pressFrom + (goal - pressFrom) * easeOutBack(t); // 半径 100% → 60%，带一次回弹
```

```glsl
// 响应段：光晕核心——距离场 + pow 衰减（完整 demo 见 demos/day1/04-光标的追随/）
vec2 p = (uv - u_mouse) * vec2(u_aspect, 1.0); // 以光标为原点的居中等比坐标
float radius = mix(0.18, 0.11, u_down);        // 按压因子驱动半径收缩，回弹曲线已在 JS 侧套好
float d = length(p);
float glow = pow(clamp(1.0 - d / radius, 0.0, 1.0), 2.0); // pow 平方衰减：中心亮、边缘急落

// 拖尾：raw 与 smooth 的差 = 速度方向；尾焰中心往速度反方向退（p 的原点在光标，所以 + vel 即取反方向）
vec2 vel = (u_mouse_raw - u_mouse) * 6.0;
float tail = pow(clamp(1.0 - length(p + vel) / (radius * 2.2), 0.0, 1.0), 2.0) * 0.4;
glow += tail;
```

### demo 05「点击的涟漪」

`u_time / u_clickTime / u_clickPos` 三枚 uniform，上一节的涟漪代码直接做主体。视觉升级只有一处：玫红主波之外叠一道天青次波，相位差 0.4——次波在进度轴上晚 0.4 启程（折合 0.48 秒），永远追在主波身后，形成双色追逐：

```glsl
// 响应段：玫红主波 + 天青次波（完整 demo 见 demos/day1/05-点击的涟漪/）
float progress = (u_time - u_clickTime) / DURATION;               // 周期 1.2s
float ringR = progress * 0.65;                                    // 最大半径 0.65
float d = length((uv - u_clickPos) * vec2(u_aspect, 1.0));

float pMain = min(progress, 1.0);
float pSub  = clamp(progress - 0.4, 0.0, 1.0);                    // 相位差 0.4：次波追着主波
float waveMain = sin(pMain * PI) * exp(-progress * 2.0);
float waveSub  = sin(pSub  * PI) * exp(-max(progress - 0.4, 0.0) * 2.0) * 0.6;

vec3 color = base
  + rose * waveMain * smoothstep(0.025, 0.0, abs(d - ringR))       // 主波：玫红
  + sky  * waveSub  * smoothstep(0.02,  0.0, abs(d - ringR * 0.85)); // 次波：半径略小，贴身后跟
```

### demo 06「滚轮的浪潮」

`chrome.pointer.wheel` 是原始累积像素（向下为正、无上界），归一化是 JS 侧的职责：这里取 600 px 滚程铺满 0–1，clamp 防越界，结果写进 `u_scroll`。回弹手感用「目标值 + 弹性追赶」实现——速度型 lerp 自带一次过冲、随后振幅指数衰减，收敛包络就是 `easeOutElastic` 0.8s 的形状；不逐事件重放 easing，是因为连续滚轮会把动画起点反复重置，弹簧在数学上正是它的连续版：

```ts
// JS 侧：wheel 原始累积 → 归一化目标 → 弹性追赶（完整 demo 见 demos/day1/06-滚轮的浪潮/）
const target = Math.min(Math.max(chrome.pointer.wheel / 600, 0), 1); // 600px 滚程铺满 0–1
scrollV += (target - scrollP) * 0.025; // 弹簧劲度：决定过冲幅度
scrollV *= 0.90;                        // 阻尼：决定 0.8s 内回稳
scrollP += scrollV;
gl.uniform1f(uScrollLoc, scrollP);
```

```glsl
// 响应段：24 条天青条纹随滚动推进（完整 demo 见 demos/day1/06-滚轮的浪潮/）
const float STRIPES = 24.0;
float phase = u_scroll * 12.56637;  // 满滚动映射相位 0–4π：两倍往返，浪潮有推有退
float band = abs(fract(uv.y * STRIPES + phase) - 0.5) * 2.0; // 三角波：0 条纹中心、1 条纹间隙
float glow = smoothstep(0.35, 0.15, band) * 0.30;            // 柔边 + 天青 30% 透明度
vec3 color = base + sky * glow;
```

三个 demo 摆在一起看：事件桥的骨架一行未改，变化的只有「哪个状态 → 哪个 uniform → 什么响应函数」。Day 1 晚间作业的 A 档「追光的萤火」与 C 档「极坐标曼陀罗」的涟漪考点，全都从这三段里长出来。

## 常见坑

| 症状 | 原因 |
|------|------|
| 在事件回调里直接 draw，拖快鼠标就掉帧 | 事件频率 ≠ 帧率：高刷鼠标每秒塞进几百次渲染请求，渲染只该发生在 rAF 里 |
| 光晕位置飘忽、窗口一缩放就错位 | 鼠标坐标没除以画布尺寸：CSS 像素（0–1600 级别）直接进 shader，值域彻底错乱 |
| 光标向左上方移动，画面里的光晕却往右下走 | 忘了 y 翻转：DOM 向下增、GL 向上增，`1.0 - y` 这步漏了 |
| 同样 0.08，换到 144 Hz 显示器手感明显变快 | lerp 系数没按帧率换算：固定系数天然帧率敏感，课程简化为 60 fps 口径并统一注明 |
| 手机上画面不动，页面自己在滚 | 没设 `touch-action: none`：浏览器把手势判定为页面滚动，pointermove 连续流被抢 |

## Checkpoint

- 能默画事件桥五环节——浏览器事件 → JS 状态对象 → 每帧 uniform 写入 → shader 响应 → 画面——并说出每个环节属于哪个世界
- 能三行内写出带 y 翻转的鼠标归一化代码：clientXY 减偏移、除画布尺寸、`1.0 - y`
- 能解释为什么不在事件回调里 draw：事件频率 ≠ 帧率，且 GPU 无事件概念、只认 uniform 当前值
- 能背 lerp 三档系数与各自手感：0.04 慢丝滑、0.08 默认、0.15 跟手，并说出 0.08 在 60 fps 下约 0.5 秒收敛
