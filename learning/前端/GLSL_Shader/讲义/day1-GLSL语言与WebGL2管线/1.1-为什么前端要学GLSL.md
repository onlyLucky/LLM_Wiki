## GLSL 到底是什么

GLSL（OpenGL Shading Language）是一门跑在 GPU 上的小型强类型语言。它和 JavaScript 最根本的差异不在语法，而在**执行位点**：JS 在 CPU 上被引擎解释执行，GLSL 被编译后烧进 GPU 的渲染管线，在两个固定位置被成千上万个线程同时执行。

| 执行位点 | 语言形态 | 执行次数 | 职责 |
|---------|---------|---------|------|
| 顶点着色器 vertex shader | 函数，输入一个顶点 | 每个顶点一次 | 算出顶点在屏幕上的位置 |
| 片元着色器 fragment shader | 函数，输入一个像素 | 每个像素一次（可能几十万次） | 算出这个像素是什么颜色 |

把 fragment shader 理解成「对每个像素执行的 `map` 回调」，你的心智模型就立住了：

```ts
// 伪代码：一次 draw call 在 GPU 上发生的事
pixels.map((pixel) => shade(pixel, time, mouse)) // shade 就是你的 fragment shader
```

区别只有一个：这个 `map` 不是引擎调度的，是 GPU 上几百万个线程**同时**执行的。你在 webgpu 课的 1.1 里见过 SIMT 的硬件原理，这里补一张语言视角的图——左边是你写的那份程序，右边是同时执行它的线程阵列：

![SIMT 并行示意：左侧一份 fragment 着色器程序（含一个 if 分支的 GLSL 代码），右侧 8×5 的像素网格，每格标注不同的 uv 坐标值，表示同一份指令在不同数据上并行执行；其中 uv.x 大于 0.5 的四列被琥珀色高亮，标注「分支发散：同一批线程里 if 的两个分支都得跑」](../../assets/diagrams/simt-parallel.svg)

对着图盯住一件事：你写的代码只有一份，但执行它的拷贝有几百万份。所以 GLSL 里没有「某个像素」的概念——**你写的不是「对某像素做什么」，而是「对一个像素做什么」**。这句话是整个 fragment shader 编程的地基，后面每一天你都在用它。

执行位点还翻转了三个你写惯了 JS 的习惯。不是语言设计者故意为难你，是执行模型决定了 GLSL 必须长这样：

| JS 里的习惯 | GLSL 里的对应物 | 为什么必须这样 |
|------------|----------------|--------------|
| for 循环遍历像素，逐个处理 | 只写「对一个像素做什么」的函数体，遍历由硬件完成 | 遍历逻辑写一次，几百万线程各自认领一个像素去执行 |
| console.log 调试中间值 | 把中间值临时写进 fragColor 看颜色 | GPU 线程没有 stdout，颜色是你唯一的「打印」 |
| 在变量里攒状态（`this.x += 1`） | 每帧从 `u_time` 重新算出整个画面 | 着色器无状态，画面是 f(time, input) 的纯函数 |

第三行尤其关键——它意味着「改画面」这件事从「改属性」变成了「改函数」。CSS 里你改 `transform`，React 里你改 props，GLSL 里你改的是画面公式本身。1.6 会把这个模型展开成完整的动画工程学。

语言形态上，GLSL 砍掉的东西比它保留的更能说明问题：

| JS 里有 | GLSL 里 | 换来什么 |
|---------|---------|---------|
| 指针与引用 | 没有，一切按值传递 | 编译器能在编译期定死每个值落在哪个寄存器 |
| 堆内存与 GC | 没有，全在栈与寄存器上 | 单次执行的耗时可预测，不会有 GC 停顿 |
| 动态类型 | 强类型 + 编译期全检 | 类型错误在编译阶段拦下，一个都到不了 GPU |
| 递归 | 没有，ES 3.00 规范明确禁止 | 调用深度编译期已知，栈分配确定 |
| 字符串与任意对象 | 没有 | GPU 的每个周期都该花在算术上 |

一门语言为一个执行模型让步到这个程度，换来的是**每一行代码的执行时间都可预测**——这也是为什么 shader 圈谈性能能精确到「这条指令用了几次乘法」。寄存器分配、无 GC、全静态检查，这些都是 GPU 能在一帧 16 毫秒里调遣几百万线程的前提。

给这个并行规模一个具体感受：一块 1920×1080 的画布约 207 万个像素，60fps 意味着你的 fragment shader 每秒被完整执行约 1.2 亿次。换算到一帧 16.7 毫秒的预算里，单像素的函数体必须在微秒级完成——这不是修辞，是后面每一天做性能决策的底数：Day 2 写 fbm 时你要算「每像素 5 次 octave 循环 × 207 万像素」的账，起点就是这个乘法。

一套 GLSL 程序不是单个文件，而是两段函数拼成的一个 program：顶点着色器回答「这个顶点落在屏幕哪里」，片元着色器回答「这块像素是什么颜色」，中间由固定功能的光栅化阶段自动衔接。先看一眼两段代码的形状——1.2 与 1.3 会把每个词讲透，1.4 教你在 JS 里把两段编译链接成 WebGLProgram：

```glsl
// vertex.glsl · 每个顶点跑一次
#version 300 es
layout(location = 0) in vec2 a_position; // 顶点缓冲区喂进来的坐标

void main() {
  gl_Position = vec4(a_position, 0.0, 1.0); // 唯一职责：报出自己在屏幕上的位置
}
```

```glsl
// fragment.glsl · 每个片元（约等于像素）跑一次
#version 300 es
precision highp float; // float 精度文件级声明，讲义 1.2 展开
out vec4 fragColor;    // 这个变量就是本像素的最终颜色

void main() {
  fragColor = vec4(1.0, 0.30, 0.43, 1.0); // 整屏玫红——最短的「会画东西」
}
```

11 行加 9 行，就是一套最小 GLSL 程序的全部。今天结束时你能读懂它们的每一个 token。顺序上有个雷先排掉：GLSL 文件的第一行永远是 `#version`。规范字面上允许它前面有空白与注释，但老驱动和部分工具链在这一点的报错五花八门——本课把它当硬纪律执行：前面什么都别放，1.3 讲预处理时细说。

顺带交代这些代码被谁编译：浏览器不编译 GLSL，**显卡驱动就是编译器**。同一份 shader 在不同 GPU、不同驱动版本上的报错措辞可能不同——这是 shader 世界的「跨浏览器兼容」本体，也是同一份代码在你两台电脑上表现不同的常见原因，不是玄学。本课所有示例取各家驱动都接受的保守写法，chrome 的错误面板再把各家的报错统一翻译成可读中文。

## 你已经在 WGSL 里见过它的影子

你在 webgpu 课写过 WGSL，那门语言的类型系统、管线思维、in/out 数据流，和 GLSL 是同一个思想的两门方言。对照表放这里，之后每次遇到语法差异回来查：

| 概念 | WGSL（你写过的） | GLSL ES 3.00（本课的） |
|------|-----------------|----------------------|
| 顶点输入 | `@location(0) pos: vec2f` | `layout(location = 0) in vec2 a_position;` |
| 片元输出 | `@location(0) fragColor` | 自己声明 `out vec4 fragColor;` |
| uniform | `var<uniform> time: f32` | `uniform float u_time;` |
| 坐标内建 | `@builtin(position)` | `gl_FragCoord` |
| 采样纹理 | `textureSample(tex, samp, uv)` | `texture(tex, uv)` |
| 精度声明 | 每个变量标 `f32/i32/u32` | 文件顶部 `precision highp float;` 一次声明 |
| 函数声明 | `fn energy(x: f32) -> f32` | `float energy(float x) { ... }` |
| 类型转换 | 显式构造 `f32(x)` | 显式构造 `float(x)`，int 到 float 无隐式转换 |

读完对照表，动手前先挑明三处工程差异——它们不改变思维，但改变你每天的写法：

1. **精度是文件级声明**：WGSL 给每个变量标 `f32/i32/u32`；GLSL 在文件头写一行 `precision highp float;`，之后所有 float 默认 highp。忘写这行，片元着色器直接编译失败——ES 3.00 的片元 float 没有默认精度，报错措辞各驱动不同，但都会指向文件头
2. **uniform 靠查地址**：WGSL 里 bind group 声明式绑定整套资源；GLSL 里每个 uniform 要 `getUniformLocation` 逐个拿「地址」再逐个赋值。1.4 里你会觉得这套接口土，但它土得透明，出了问题一查便知
3. **内建变量长在关键字里**：`gl_Position`、`gl_FragCoord`、`gl_VertexID` 是语言内建；WGSL 的对应物是 `@builtin(...)` 显式标注。GLSL 省事，WGSL 明白，各取所好

结论很直接：**你学的是同一套思维，换一门方言**。本课不重复讲管线原理（对象模型、bind group、渲染 pass 在 webgpu 1.2 与 1.3 已讲透），所有精力都花在「用这门语言画出东西」上。

花 30 秒做个翻译练习：回想你在 webgpu 课写的第一个 WGSL fragment，在脑内把它换成 GLSL——改动其实只有三处：`fn` 换成返回类型前置、`@location` 换成 `in/out`、`var<uniform>` 换成 `uniform`。做完这个练习，WGSL 与 GLSL 的差异对你就从「两门语言」降维成「几处方言口音」。

## 创意网站用 GLSL 在做什么

你逛过的那些让你停在页面上的网站，它们的「氛围」九成来自 fragment shader。四类典型用途，每一类你在实例清单里都能找到对应站点：

| 用途 | 画面特征 | 典型站点 | 本课哪一天拿下它 |
|------|---------|---------|----------------|
| 全屏背景流动 | 噪声驱动的缓慢流场，像液体或云 | [igloo.inc](https://igloo.inc) | Day 2（2.4 噪声与 fbm） |
| 图片 hover 失真 | 鼠标划过时图片局部扭曲、RGB 错位 | [lusion.co](https://lusion.co) | Day 3（3.2） |
| 滚动转场 | 滚动驱动 shader 进度，画面被遮罩推开 | [orage.studio](https://orage.studio) | Day 3（3.3） |
| 粒子成型 | 几万颗粒子从混乱聚成 logo 或文字 | [activetheory.net](https://activetheory.net) | Day 3（3.4） |

四类各拆一个站点的画面逻辑，看看那「几十行」到底在算什么：

**igloo.inc · 全屏背景流动**——冰川场景里永远有一层缓慢翻涌的雾。雾没有形状也没有边界，因为 fragment 里用 fbm（多倍频叠加的噪声）扰动 UV 后采样亮度：每个像素独立算一遍噪声，拼出来才是「场」而不是「物」。没有 GPU 的逐像素并行，这种画面在 JS 里画一帧就要卡一次。完整配方在 2.4。

**lusion.co · 图片 hover 失真**——鼠标划过作品卡片，图片像果冻一样局部凹陷，RGB 三个通道被错位撕开。拆开是三步：fragment 拿鼠标位置算一张「扰动强度图」，UV 依强度偏移，再对 R/G/B 各采样一次、各偏移一点，一次 mix 缝回去。三次采样一次混合，Day 3 的 3.2 拿它当入门案例。

**orage.studio · 滚动转场**——滚动条每推一格，就有一个 uniform（进度 0 → 1）被写进 shader，一块圆形遮罩以进度为半径推开新画面。遮罩是 smoothstep 画的圆边，转场手感来自 JS 侧的缓动函数——「JS 管时间线、shader 管遮罩」这套分工，就是 1.7 事件桥模式的进阶版。

**activetheory.net · 粒子成型**——首页几万颗粒子聚成品牌字。每颗粒子是一个顶点，顶点着色器用噪声把初始位置推向目标位置，混合系数就是时间——你会在 1.6 学到的 u_time，在这里驱动「混乱到秩序」的整场演出。密度感来自每颗粒子独立的噪声位移，又是「对一个粒子做什么」的复用。

注意共同点：这些效果的「前端工程」部分都不难——一个 canvas、一个 render loop、几个事件监听，你都写过一百遍。难的是 shader 里那几十行视觉算法，而这正是本课三天要交付给你的能力。

观察力的训练比清单更值钱：逛 [awwwards.com](https://www.awwwards.com/) 时打开 DevTools 的 Sources 面板，全局搜 `.glsl`、`fragment` 或 `#version`——大量创意网站的开发版资源里能直接翻到 shader 源码，读别人的 shader 是这个领域性价比最高的进阶方式。本课根目录的《实例网站清单》收录了三十多个值得这样拆的站点，Day 2 结束后你会带着新眼睛重访它们。

反过来说一句有取舍的话：不是所有动效都该上 shader。CSS transition 能覆盖的 hover、Canvas 2D 能画好的图形、SVG 滤镜能做的位移，都别动用 GPU 管线——shader 的成本按全像素计，为一条下划线动用它不仅浪费，还会丢掉文本可访问性与 SEO。判断标准就一句：**效果需要逐像素计算，才值得 GLSL**。

## 为什么是 WebGL2 而不是 WebGPU

2026 年，创意网站的主流运行时仍是 WebGL2，原因有三：Three.js 的默认渲染器、成熟材质生态、以及全球浏览器的兼容覆盖率——WebGPU 在 Safari 和部分移动端仍有落空场景。创意工作室交付作品时不会为一个 shader demo 放弃 Safari 用户。

交付视角的账再算细一点：

| 视角 | WebGL2 | WebGPU |
|------|--------|--------|
| 浏览器覆盖 | 全平台可用，Safari 稳定版与主流移动端全支持 | Chrome/Edge 全量，Safari 与部分安卓仍有缺口 |
| 生态位 | Three.js 默认渲染器，十年素材与教程积累 | WebGPURenderer 在快速追赶 |
| 创意社区 | awwwards 级 shader 作品的绝对主流 | 前沿实验场 |
| 本课的位置 | Day 1–2 的主战场 | Day 3 收尾时给完整的迁移地图 |

所以本课的语言是 GLSL ES 3.00（WebGL2 的 shader 方言），API 是 WebGL2。你在 webgpu 课学的知识不会浪费——管线哲学是通的，而且 Day 3 会告诉你 WebGPURenderer 与 TSL 如何把这套 GLSL 思维搬回 WebGPU。

GLSL ES 3.00 与桌面版 GLSL 的关系一句话带过：前者是后者的精简子集（去掉部分动态特性，强制声明精度），本课只碰 ES 3.00，所有写法在 WebGL2 与 Three.js 的 ShaderMaterial 里通用。

先原生、后框架的顺序也在这里说定：Day 1–2 全程原生 WebGL2，因为框架会把 shader 藏在抽象后面，而你要学的恰恰是藏在后面的那层。Day 3 把同样的 GLSL 放进 Three.js 的 ShaderMaterial——GLSL 一行不变，变的只是喂 uniform 和接事件的方式。

## How：跑通本课程的第一个页面

先看全景——一次 draw call 在 GPU 上流过的五个阶段，可编程的只有头尾两个：

![GLSL 渲染流水线五阶段图：顶部一条天青色 uniform 总线标注「uniform：全局广播，同一个值，顶点与片元都能读」；五个节点横向排列——顶点着色器（输入 attribute，输出 gl_Position 与 varying）→ 图元装配（输入顶点流，输出图元序列）→ 光栅化（输入图元，输出片元与插值后的 varying）→ 片元着色器（输入插值后 varying，输出 fragColor）→ 输出合并（输入 fragColor 与深度，输出屏幕像素）；光栅化节点下方有琥珀色标注框「varying 在这里插值——三个顶点值，几十万次免费平均」；底部注释：一个三角形走完全程，顶点着色器跑 3 次，片元着色器跑几十万次](../../assets/diagrams/shader-pipeline.svg)

对着图从左到右过一遍：顶点着色器只跑 3 次（三角形只有三个顶点），光栅化把三角形切成了几万个片元，片元着色器对每个片元跑一遍你的代码。**你的 GLSL 代码 95% 写在片元阶段，成本也几乎全在片元阶段**——这是后面所有性能讨论的前提。图顶那条 uniform 总线也别放过：它是 JS 每帧向 GPU 广播的参数（时间、鼠标、分辨率），从 1.5 起你会跟它朝夕相处。图里琥珀色标注框是另一条数据通路：顶点着色器只算 3 次颜色，几十万个像素的颜色由光栅化免费插值——这是 GPU 送你的第一份并行红利，varying 机制在 1.4 正式登场。

| 程序编译 | `createProgram(gl, vsSource, fsSource, chrome)` | 编译链接两段 GLSL，报错带行号直达页面 |
| 几何与 uniform | `bufferData` / `getUniformLocation` | 喂顶点数据，拿到 uniform 的「地址」 |
| 帧循环 | `chrome.startLoop((now) => { ... })` | 每帧写 uniform、清屏、`drawArrays` |

五个段落各展开两句，先混个脸熟，1.4 会逐段拆到每一行为止：

**chrome 接入**——`createChrome` 是课程的教学外壳：左上课程信息、右上技术标签、左下操作提示、右下实时 FPS，外加 800ms 入场淡入。它还内置了一个交互状态桥 `chrome.pointer`（原始坐标、平滑坐标、按下状态、滚轮累积），1.7 会让它唱主角。

**GL 初始化**——`initGL` 向 canvas 要 `webgl2` 上下文，拿不到不抛异常，而是在页面上给出中文指引（硬件加速被关、驱动进黑名单是两大主因）。WebGPU 课里这叫 `requestAdapter` 失败——同一件事，不同 API 的说法。

**程序编译**——`createProgram(gl, vsSource, fsSource, chrome)` 把 vertex 与 fragment 两段源码编译链接成一个 WebGLProgram，失败时把编译错误连同 shader 源文件的行号直接显示在页面错误面板上。这是本课第一教学设施，1.4 会拆开这层封装手写一遍。

**几何与 uniform**——`bufferData` 把三角形三个顶点的数据喂进 GPU（每个顶点 5 个 float：位置 2 个 + 颜色 3 个，交错排列）；`getUniformLocation` 拿到 `u_time`、`u_mouse` 等 uniform 的「地址」，供帧循环每帧写入。WebGPU 里 bind group 管的事，在这里是「查地址 + 赋值」两件小事。

**帧循环**——`chrome.startLoop` 包好了 requestAnimationFrame 与毫秒转秒的时间换算；回调里每帧固定三步：写 uniform → 清屏 → `drawArrays`。整条渲染命令就这三个动作，画面却在每一帧重新诞生——1.6 的「纯函数动画模型」物理基础就在这里。

提前打个预防针：你接下来写 shader 的主要搭档不是文档，是错误面板。GLSL 编译错误的报错文化与 tsc 几乎一样——行号、类型、期望什么得到什么，只是方言是 GPU 的。课程把它做成页面内的一等公民：编译失败不是控制台里一闪而过的红色，而是常驻画面、可读、可行动的中文提示。1.4 教你读报错，之后每一天你都在用它。

这 74 行里你今天只需要读懂结构。动笔改点什么，三个实验由浅入深：

1. 把 `fragment.glsl` 里的 `0.06 * sin(u_time * 0.8)` 改成 `0.2 * sin(u_time * 3.0)`——呼吸变快变猛（这两个数字 1.6 会拆开讲）
2. 把 `vec3 shifted = mix(v_color, pull, 0.15);` 里的 `0.15` 改成 `0.6`——鼠标拉动色相的幅度从「轻微」变成「明显」
3. 把 `ROSE` 的值换成琥珀 `vec3(1.0, 0.757, 0.271)`（#FFC145 的 0–1 浮点换算）——渐变起点换色

三个实验都是「改一行、保存、看画面」。你已经体验了这套开发节奏：没有打包、没有状态恢复，保存即所见，错误面板与热更新就是未来三天的工作流。动完三个实验，把 fragment.glsl 恢复原样再往下读——从 1.2 起，讲义里的代码对照都以 demo 01 的原版为准。

## 常见坑

| 症状 | 原因 |
|------|------|
| `npm run dev` 报 module 找不到 | 没装依赖。clone 后必须先 `npm install`，Vite 的依赖都在 node_modules 里 |
| 页面白屏，控制台报 `Failed to load module script` | 直接双击 index.html 用 file:// 协议打开。ES module 在 file:// 下被浏览器拦截，必须走 dev server |
| 保存 .glsl 后终端报 404 | `?raw` 导入的相对路径写错。路径以 main.ts 所在位置为基准，应为 `./shaders/fragment.glsl?raw` |
| 画布区域灰屏，错误面板提示 WebGL2 不可用 | 浏览器禁用了硬件加速。Chrome/Edge 检查「设置 → 系统 → 使用硬件加速」，Firefox 检查 `webgl.disabled` 配置 |
| 换浏览器或换机器后 dev server 起不来 | 显卡驱动进了浏览器黑名单（老核显常见）。换 Chrome 或更新驱动；虚拟机里大概率没有 GPU 直通 |
| 改了 shader 画面没变化 | `?raw` 导入的热更新对 .glsl 文件部分场景失效，手动刷新页面即可 |
| 隐身模式打开页面，WebGL2 不可用 | 部分隐身配置或扩展禁了 GPU 进程。换普通窗口验证，再排查扩展 |
| 编译通过，画面却全黑 | fragment 没给 `out` 变量赋值——输出是未定义值。与另一种死法区分：缺 `precision highp float;` 是直接编译失败，错误面板会拦下（1.2 讲） |
