## 3. 规格颗粒度硬标准（闸门一）

课规格是唯一施工图。三张颗粒度清单，制定侧写规格时逐条对齐，执行侧开批前先检查——**不达标的规格退回制定侧，不得开批**。黄金样例：`01-第1课-规格.md`。

讲义规格必须写到：

- blockquote 头全文（标题 / 课次模块 / 时长 / 理论对照）
- 章节大纲到 H2，每节给出要点、表格行数、代码段主题、比喻锚点
- 常见坑表 4–6 行（症状 + 原因，来自真实易错点）
- Checkpoint 条目、引用的 demo 与图

代码规格必须写到：

- 文件树（每个文件的职责一句话）
- 类 / 函数签名含类型注解；常量名与取值
- 分段职责（run.py 的 S1/S2… 每段做什么，讲义 How 段与之对应）
- 验收测试：pytest 用例名 + 每条断言什么（mock 策略写明，测试不花真钱）
- README 关键点 4 条 + 常见报错表预填 4–6 行

作业规格必须写到：

- 三档各一段目标（对标什么真实场景）
- 每条 TODO 的编号 + 位置（文件 + 函数）+ 做什么
- 每档验收标准 3–5 条可观察项
- 提示三档的内容方向（思路 / API 名 / 伪代码）

## 4. 讲义模板（六段式）

文件名 `讲义/NN-主题/N.M-标题.md`，长度纪律 250–400 行（低于 200 说明没讲透，超过 400 拆两篇）：

```markdown
# N.M 标题（问题式或断言式）

> 第 N 课 · 模块 M · 约 XX 分钟
> 理论对照：《AI-Agent-动画短剧工具-学习路线.md》模块 X「……」——一句话分工

导语：两三句。第一句钩子；最后一句预告本篇讲什么。

## Why：本篇存在的理由
## What：核心概念（表格与 mermaid 优先，比喻锚点落在这里）
## How：demo XX 逐段精讲（对照 S1/S2… 分段，固定节）
## 常见坑（症状 | 原因，5–6 行）
## Checkpoint（4–5 条「能说出 / 能解释 / 能写出」）
## 相关材料（demo 路径 + 前情讲义编号 + 延伸阅读）
```

图示约定：本课程不维护 SVG 资产，讲义内嵌 mermaid（结构图用 `flowchart`、状态用 `stateDiagram`），图的内容要点在课规格里写明。

- 课级 `homework/NN/README.md`：骨架哲学段 + 三档总览表（档 × 目录 × 考点 × 前置讲义 × 参考时长）+ mermaid 递进图 + 「为什么是这三题」段

## 7. 写作风格（反 AI 味，最高优先级）

禁用词表（每批 grep 自查，段首命中即改写）：「首先 / 其次 / 再次 / 最后（作段落开头时）/ 总而言之 / 综上所述 / 值得注意的是 / 让我们 / 我们一起来 / 在本节中 / 不难发现 / 众所周知 / 简而言之 / 接下来我们将 / 希望本文 / 本文将介绍」。

句式规则：

- 先结论后论证：每段第一句就是结论（导语除外）
- 第二人称直接对话：「你会」「你写」，像资深同事结对编程
- 有观点、有取舍：写「这一步 90% 的场景用这条路径」而不是「有多种方法可以选择」
- 表格优先于段落；每篇讲义至少一处可单独摘抄的金句

比喻库（面向前端学员的知识锚点）：

| Agent 概念 | 前端锚点 |
|---|---|
| Agent 循环 | 自己手写的 rAF 渲染循环——每帧问一次「下一步做什么」 |
| Function Calling | 受控组件的 onChange 注册——模型只发事件，执行在你 |
| MCP | 工具界的 npm 协议——任何模型都能 import 任何工具 |
| Embedding | 给每句话发一个有语义的 IP 地址，相近的话住在隔壁 |
| RAG | 渲染前先查数据库——把检索结果当 props 注入 |
| LangGraph 状态 | 组件树共享的 store——节点只读写 store，不互相 import |
| checkpointer | 会话版 localStorage + 时间旅行调试器 |
| DAG 拓扑执行 | vite 打包时按依赖图决定 bundle 顺序 |
| 节点 Schema | TypeScript interface 即合约 |
| System One 三原语 | 三种类型化回调：onChange / onScore / onConfirm |
| LoRA | 给大模型外挂一层 CSS 变量主题包，不动原文件 |

## 8. 每批自查清单（闸门三，全部可执行）

按顺序执行，结果写进 PROGRESS 备注：

1. `uv run pytest` 全绿（贴测试统计行 `N passed`）
2. 每个 demo 冒烟一次：`uv run python demos/NN-名称/run.py --mock`，输出前几行贴进备注——只写「完成」按未完成论
3. 禁用词 grep：`grep -n "首先\|其次\|值得注意\|让我们" 讲义/作业/README 目标文件`，段首零命中
4. 路径存在性：逐条核对文中引用的 demo / 讲义 / 文件路径真实存在（grep 文件名）
5. TODO 编号唯一：grep 全仓库 `TODO(` 无重复
6. 行数纪律：讲义 250–400 行
7. 规格对照：把课规格里的验收点抄成 checklist，逐条勾选
8. 升级单：本批卡过的地方单独列出（位置 / 现象 / 两次尝试 / 是否已升级）

## 9. 审计-返工-复验闭环（闸门四，制定侧执行）

每课代码批完成后，制定侧出 `_制作计划/审计/NN-审计单.md`，口径对齐 GLSL 课《05-完整度与质量审计报告》：

| 维度 | 检查内容 | 合格线 |
|---|---|---|
| 结构完整度 | 四件套 100%、行数纪律、TODO 编号 | 10/10 |
| 内部链接 | 引用路径逐条可达 | 零坏链 |
| 写作风格 | 禁用词段首零命中、Checkpoint/常见坑齐全 | 零违规 |
| 可运行性 | pytest 全绿 + 冒烟证据（--mock 与真实模式抽查） | 全部可跑 |
| 技术正确性 | 讲义与 README 代码段行号级校对、API 版本核对（openai ≥ 1.x、pydantic v2、bpy 4.x） | 无「照抄即错」 |

- 问题分级：P0（跑不起来 / 照抄即错）当日修复；P1（坏链 / 技术口径错误）次批修复；P2（表述 / 长度）结营前统一修
- 每条问题给：位置（文件 + 行号）/ 现象 / 根因 / 修法——返工单直接可执行
- 修复后复验：重跑受影响的自查项，结果追加进审计单「修复记录」节；PROGRESS 该批备注补记「复验通过」

## 10. PROGRESS 与升级单格式

PROGRESS 表列不变：批次 | 内容 | 状态 | 日期 | 备注（备注必须含冒烟证据或审计结论）。升级单写在当课规格末尾「升级预案」节：位置 / 现象 / 两次尝试 / 需要制定侧做什么。
