## 第 2 课目标能力清单

学员在第 2 课结束时能：

1. 用系统提示词 + 人设约束把模型的输出风格与边界管起来，并解释「约束写在 system 还是 user」的取舍
2. 给同一任务写零样本 / 少样本 / CoT 三种提示，并说出各自适用场景
3. 用 Pydantic 给业务对象（剧本）定义 JSON 合同，把模型的自由文本约束成合法结构
4. 实现「校验失败 → 错误回灌 → 重试 ≤3 次」的结构化输出闭环，并产出校验报告
5. 解释 temperature、max_tokens 对 JSON 完整性的影响（第 1 课 1.4 的落地）

## 讲义 2.1 规格 · 系统提示词与角色设定

```markdown
# 2.1 系统提示词与角色设定：给模型发一份「入职通知」

> 第 2 课 · 模块 1 · 约 55 分钟
> 理论对照：《学习路线》模块一「Prompt 工程」——路线列知识点，本篇给剧本场景的实操版
```

**章节大纲**：

- 导语：第 1 课你的模型什么都聊；今天起它只做你要的事——第一道工序就是 system 提示词
- `## system 与 user 的分工`：对照表（角色 / 优先级 / 生命周期）；结论句「system 是劳动合同，user 是工作任务单」
- `## 一份合格的编剧人设长什么样`：五要素模板（身份 / 职责 / 风格 / 禁止 / 输出格式预告）+ 三版对比（无约束 / 松约束 / 紧约束的输出差异，各贴一段 mock 输出）
- `## 约束的三层强度`：硬约束（输出格式）/ 软约束（风格）/ 禁止事项（负面清单）；「禁止事项要写成可验证的句子，不写成形容词」
- `## How：demo 02 的 system 提示词逐句拆解`（每句标注它约束的是五要素的哪一条）
- `## 常见坑`（5 行）：把所有要求堆进 user（每轮都要重复）/ 人设写成形容词堆（「专业、严谨、有创意」不可验证）/ 禁止事项与任务自相矛盾 / system 里塞示例导致指令稀释 / 换模型后人设失效（长度与位置敏感性）
- `## Checkpoint`：能写出五要素人设；能说出三层约束各管什么；能给一段输出判断它违反了人设的哪一条

## 讲义 2.2 规格 · few-shot 与思维链

```markdown
# 2.2 few-shot 与思维链：给模型看例题，还是教它打草稿

> 第 2 课 · 模块 2 · 约 50 分钟
> 理论对照：第 1 课 C 档实验室已经跑过对照——本篇给方法论名字
```

**章节大纲**：

- 导语：昨晚实验室的数据先对答案——三种提示的正确率与 token 账单差异，就是本篇的导论
- `## 零样本：什么时候够用`：任务本身高频常见时零样本最优（便宜）；判断标准三条
- `## few-shot：例题怎么选`：2–3 个覆盖典型输入输出的例；例的多样性与边界例（一个正常例 + 一个边界例的配比）；「例题是隐式的 schema」
- `## 思维链：让模型把草稿打在卷面上`：CoT 触发三式（「一步一步想」/ 关键步骤列举 / 输出结构里预留 reasoning 字段）；代价（输出 token 翻倍）与适用（多步推理，不适用纯抽取）
- `## 对比表`：三种方式 ×（正确率倾向 / token 成本 / 适用任务）× 本课程用在哪一课
- `## How：demo 02 的分镜生成提示里 few-shot 怎么嵌`（一条示例分镜占位、新任务怎么替换）
- `## 常见坑`（5 行）：例题与真实任务格式不一致 / 例题太多挤占上下文 / CoT 用在简单任务上白花钱 / 把 CoT 文本当结构化输出解析 / 例题答案本身有错（模型学走错误）
- `## Checkpoint`：能为一项任务选提示方式并说明理由；能写出带边界例的 few-shot；能说出 CoT 的代价

## 讲义 2.3 规格 · JSON Schema 约束与 Pydantic 解析

```markdown
# 2.3 JSON Schema 约束与 Pydantic 解析：给剧本发一份合同

> 第 2 课 · 模块 3 · 约 60 分钟
> 理论对照：《学习路线》模块一「结构化输出」——本篇把 Pydantic 从环境变量推到业务对象
```

**章节大纲**：

- 导语：Agent 世界的通货不是文本，是结构——第 9 课的分镜 JSON、第 10 课的节点 I/O，都从今天这份合同开始
- `## 剧本合同长什么样`：Pydantic 四模型全文（与 demo 02 规格一致：`Character` / `Line` / `Scene` / `Script`）；逐字段讲约束（`scenes: list[Scene] = Field(min_length=1)`、`text: str = Field(min_length=1, max_length=120)`——为什么给台词限长：口型与时长对齐的后置约束）
- `## Pydantic = zod 的 Python 表亲`：等价写法三行对照（Field 约束 ↔ zod 的 .min()/.max()）；`model_json_schema()` 直接喂给模型当格式说明书
- `## 三种让模型吐 JSON 的姿势`：提示词内嵌 schema / `response_format={"type": "json_object"}` / 函数调用强制结构——取舍表（兼容性 vs 强制度），本课用姿势一 + Pydantic 兜底校验
- `## 校验失败怎么办`：`ValidationError` 的 errors() 怎么读（loc / msg 两列够用）；把错误清单拼成一句回给模型——「错误回灌」第一次出场（第 2.4 讲展开成闭环）
- `## How：demo 02 的 models.py 与解析段逐行拆解`
- `## 常见坑`（6 行）：忘 min_length 导致空场景 / 模型输出 JSON 外包了一层 ```json 代码围栏（先剥围栏再解析）/ max_length 限太严模型只好截断台词 / 嵌套模型忘了 import / 模型把字段名自作聪明改近义（persona→personality）/ temperature 过高破坏 JSON 稳定性
- `## Checkpoint`：能徒手写出四模型；能把一条 ValidationError 翻译成人话；能说出三种姿势的取舍

## 讲义 2.4 规格 · 结构化输出的失败与重试

```markdown
# 2.4 结构化输出的失败与重试：三振出局，错误回灌

> 第 2 课 · 模块 4 · 约 40 分钟
> 理论对照：《学习路线》模块五「重试与降级」——本篇是它的第一次落地，第 4 课再扩展到工具层
```

**章节大纲**：

- 导语：昨天的合同今天就会被违约——本篇写的是违约处理流程，它决定你的管线是玩具还是工具
- `## 失败的四种脸`：非法 JSON（截断 / 围栏 / 闲聊）/ 合法 JSON 但缺字段 / 字段类型错 / 语义合规但内容空转；各自的探测点在哪一层
- `## 错误回灌三明治`：重试 messages 的结构（原任务 + 上次输出 + 错误清单 + 「只修错误，输出完整 JSON」）；为什么每次重试都要带上次的完整输出（模型不知道自己错哪）
- `## 重试上限与降级`：MAX_RETRIES=3 的三振出局；三次失败后的降级路径（存错误现场 → 人工补单接口预留）；`finish_reason=length` 时提高 max_tokens 再试——第 1 课 1.4 伏笔的回收
- `## 校验报告`：一次生成会留下什么（script.json / report.md：尝试次数、每轮错误、最终 token 成本）——为第 15 课埋点打样
- `## How：demo 02 的重试循环逐段精讲`
- `## 常见坑`（5 行）：无限重试没有上限 / 重试不带历史（模型重复犯错）/ 用 try/except 把错误吞了（报告里看不到失败）/ 把降级当失败处理 / temperature 不降（重试时降到 0.1）
- `## Checkpoint`：能画出重试状态机（生成→校验→回灌→三振出局）；能写出校验报告的字段清单；能说出哪种失败该提高 max_tokens、哪种该降温度

## demo 规格 · 02-剧本JSON生成器

| 项 | 规格 |
|---|---|
| 路径 | `demos/02-剧本JSON生成器/`（README.md / run.py / tests/test_run.py / models.py） |
| 行为目标 | 输入一句话创意 → 合法剧本 JSON（`assets/02/script.json`）+ 校验报告（`report.md`）；校验失败错误回灌重试 ≤3 次；`--mock` 返回固定合法样例与一次故意失败样例（`--mock-fail-once`）走完整重试路径 |
| 接口约束 | `models.py` 四模型：`Character(name: str, persona: str)`；`Line(character: str, text: str = Field(min_length=1, max_length=120))`；`Scene(location: str, action: str, lines: list[Line] = Field(min_length=1))`；`Script(title: str, logline: str, characters: list[Character] = Field(min_length=1), scenes: list[Scene] = Field(min_length=1))`；run.py：`generate_script(idea: str, client: ChatClient, max_retries: int = 3) -> tuple[Script, dict]`（第二项为报告元数据：attempts / errors / usage） |
| 分段结构 | S1 输入与 schema 提示构造（system 内嵌 `model_json_schema()` + few-shot 示例分镜）→ S2 解析（剥代码围栏 → json.loads → Script.model_validate）→ S3 错误回灌重试循环（temperature 首轮 0.2、重试 0.1；length 截断时 max_tokens +512）→ S4 落盘（script.json + report.md）→ S5 mock 分支 |
| 验收测试 | `test_valid_idea_produces_script`（mock 合法样例：attempts==1 且校验通过）/ `test_retry_on_validation_error`（mock-fail-once：attempts==2 且最终合法）/ `test_strikes_out_after_three`（mock 恒错：抛出自定义 `ScriptGenerationError` 且 report 记录 3 轮错误）/ `test_report_written`（report.md 存在且含 attempts 与 token 合计） |

**README 关键点 4 条**：① 为什么 schema 内嵌提示而不是函数调用强制（兼容三通道）② 剥代码围栏的兼容层位置 ③ 错误回灌的 messages 长什么样（贴一段）④ report.md 与第 15 课埋点的关系。

**常见报错预填**：json.loads 抛 JSONDecodeError（围栏或截断）/ ValidationError 的 loc 读法 / 模型返回 `{"script": {...}}` 多包一层（prompt 明确「直接输出 Script 对象」）/ temperature 0.9 时不稳定 / mock 模式忘记 flag 导致真实计费。

## 升级预案

- `response_format` 与函数调用两种姿势在各通道行为不一致：执行侧遇到 mock 无法模拟的情况，优先在 MockChatClient 里补桩，桩补不了即升级
- Pydantic v2 的 `model_validate` 与 v1 `parse_obj` 混用是高频翻车点：讲义只写 v2 API；执行侧 grep `parse_obj` 出现即返工
- few-shot 示例分镜的选材需要制定侧终审（示例质量决定讲义可信度）——执行侧不得自造示例，用规格附录里的示例
