## 讲义 4.1 规格 · Function Calling：schema 定义与调度循环

```markdown
# 4.1 Function Calling：模型亲手填调用的时代

> 第 4 课 · 模块 1 · 约 60 分钟
> 理论对照：《学习路线》模块一「工具调用」——路线给全景，本篇给协议级实现
```

**章节大纲**：

- 导语：第 3 课你自己拼 schema 提示、自己解析模型回复；官方 Function Calling 把这两件事变成协议——模型直接吐结构化的 tool_calls，解析零成本
- `## 从文本协议到结构协议`：第 3 课「提示里塞 schema + 文本解析」vs 本课「tools 参数 + tool_calls 字段」对照表（可靠性 / token 成本 / 调试难度三行）；结论「自研解析是练内功，协议调用是上生产」
- `## tools 声明五要素`：type/name/description/parameters/required；description 是写给模型的文档——「描述含糊，模型就瞎调」，正反两段 description 对照
- `## 调度循环三段`：发送（messages + tools）→ 解析（`msg.tool_calls` 数组）→ 执行回灌（role=tool + tool_call_id）；并行调用代码段（一个回复里多个 call 依次执行再一起回灌）
- `## How：demo 04 的 get_weather 链逐段精讲`（对照 S1–S3 分段）
- `## 常见坑`（5 行）：枚举不收窄（城市名自由发挥拼出幻觉 URL）/ description 写成给人看的 / 忘回灌 role=tool / tool_call_id 对不上 / 并行调用只执行第一个就回灌
- `## Checkpoint`：能默写调度循环三段；能说出 description 的读者是谁；能解释并行调用为什么全部执行完才回灌

## 讲义 4.2 规格 · 错误处理：重试、超时与工具降级

```markdown
# 4.2 错误处理：没有超时的工具调用都是定时炸弹

> 第 4 课 · 模块 2 · 约 45 分钟
> 理论对照：《学习路线》模块五「重试与降级」——工具层的第一次落地
```

**章节大纲**：

- 导语：第 3 课的坑表说过「工具异常不炸循环」；今天把这句话升级成三层防线
- `## 工具失败的三种脸`：自身异常 / 超时 / 返回不可用（空值、格式崩坏）；各自的探测层
- `## 重试一次原则`：`RetryOnce` 装饰器代码段；可重试（网络抖动、超时）与不可重试（参数错误——应回给模型改参）判别表
- `## 降级路径`：重试仍败 → 返回「工具暂不可用」观察 → 模型换路作答；降级是给模型的台阶，不是给用户的道歉信
- `## 超时预算`：每个工具调用默认 10s 上限（常量）；与第 15 课埋点的连接（每次降级都是一条样本）
- `## How：demo 04 的 RetryOnce 与降级分支`
- `## 常见坑`（5 行）：无限重试 / 重试不换任何东西（纯烧钱）/ 吞异常导致观察缺位 / 把参数错误当网络错误重试 / 并行调用一个失败全批作废
- `## Checkpoint`：能写出 RetryOnce 装饰器；能判断三类错误哪些重试哪些回灌；能说出降级观察的文案为什么面向模型而不是用户

## 讲义 4.3 规格 · MCP：协议全景与自建 Server

```markdown
# 4.3 MCP：工具界的 npm 协议

> 第 4 课 · 模块 3 · 约 60 分钟
> 理论对照：《学习路线》模块二「MCP」与第 3 章框架入门——本篇做第一个 Server
```

**章节大纲**：

- 导语：M 个模型各自接 N 个工具要写 M×N 份胶水；MCP 把它压成 M+N——一座桥对齐所有人
- `## M×N 问题图`：mermaid（左边三个模型、右边五个工具的蜘蛛网 → 中间插 MCP 一条总线）；与第 3 课「npm 协议」比喻会师
- `## 三原语`：tools / resources / prompts 一行表（本课只用 tools）；传输方式 stdio 与 http 一句话分工
- `## 最小 Server`：Python SDK 的 `@mcp.tool()` 装饰器（版本以实测为准，定位方法同 3.3）；工具函数即服务；客户端连接与工具发现
- `## 与 ToolRegistry 的关系`：对照表三行（声明方式 / 进程位置 / 可复用范围）；结论「MCP 是把注册表搬到进程外——同一份工具，任何客户端可用」，demo 04 两种暴露并存
- `## How：demo 04 的 server_file_tools.py`
- `## 常见坑`（5 行）：stdio 启动命令路径错 / Server 崩了客户端的报错长相 / SDK 版本漂移（用定位方法不背 API）/ 客户端忘开工具授权 / sandbox 路径在 Server 侧失守
- `## Checkpoint`：能画出 M×N 到 M+N 的图；能说清三原语各自给谁用；能对照注册表与 MCP 的取舍

| 分段结构 | S1 工具定义与枚举 schema → S2 调度循环（tools 声明 + tool_calls 解析 + 全部执行后统一回灌）→ S3 RetryOnce 与降级分支 → S4 MCP Server 独立文件 → S5 mock 脚本驱动 |
| 验收测试 | `test_parallel_tool_calls`（一次任务触发两个工具且都执行）/ `test_retry_once_on_timeout`（mock 抛 TimeoutError 一次后成功，调用计数 == 2）/ `test_degrade_after_retry`（连续两次超时 → 观察含「工具暂不可用」且循环不崩）/ `test_sandbox_blocks_outside_path`（写 `../x` 返回失败观察，无文件产生）/ `test_enum_rejects_unknown_city`（schema 层拒绝枚举外输入） |

**README 关键点 4 条**：① 并行调用「全部执行完再统一回灌」的原因 ② 白名单在工具侧而不是模型侧 ③ RetryOnce 的可重试白名单 ④ 同一工具「本地注册表 / MCP Server」两种暴露的启动方式对照。

**常见报错预填**：tool_call_id 不匹配报 400 / 枚举外城市名被 schema 拒绝的长相 / 超时未设导致挂死 / sandbox 越界观察文案 / stdio Server 启动路径错误。

## 升级预案

- MCP Python SDK 迭代快：讲义只写定位方法与最小骨架，执行侧先 `pip show` / 官方文档实测再落笔；API 不符即升级
- 真实天气 API 需要 Key 且不稳定：demo 一律用内置 mock 数据源，真实接入作为讲义延伸阅读，不作验收
- stdio 跨平台差异（Windows 命令行引号）：README 写 macOS 主路径，其他平台标注「见 SDK 文档」
