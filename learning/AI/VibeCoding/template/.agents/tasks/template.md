## 任务生命周期（创建 / 领取 / 修改 / 完成 / 验收）

> 任务清单是**持续补充、动态分级的待办队列**，不是一次性执行的静态清单。以下规则约束它如何演变。

| 环节 | 规则 |
|------|------|
| 创建 | 计划外新任务先登记到清单并分配 ID，写清目标、范围、验收与依赖；需求不清晰时先登记到 [prd.md](../specs/product/prd.md) 的「待解决问题」，不得直接开工 |
| 分级 | 按优先级（P0/P1/P2）动态调整排序，调整时在任务详情记录原因 |
| 领取 | 同一时刻只允许一个「进行中」；领取前确认依赖任务已完成 |
| 修改 | 目标、范围、验收标准变更时必须更新详情并注明变更原因，**禁止静默修改验收标准** |
| 完成 | 逐条核对验收项，在详情中填写证据后置为「待评审」，经评审通过才置为「完成」 |
| 验收 | 由人确认证据可信；证据不齐全视为未完成，退回「进行中」 |

## 拆分原则

- 单个任务应能在 [半天内] 完成，可独立验证
- 任务粒度对应 `../specs/product/user-stories.md` 的一个故事或一个接口
- 依赖关系必须显式标注，避免并行冲突

## 证据链约定

- 任务置为「完成」前必须在详情中填写证据，证据与 [验收标准](../specs/product/acceptance-criteria.md) 及 [验收证据映射](../specs/quality/acceptance-evidence.md) 对应
- 证据须可追溯到具体版本（提交哈希 / CI 链接 / 日志路径），"应该没问题"不算证据
- 完成任务后同步追加一条开发日志（见 `../logs/README.md`），形成「任务 → 证据 → 日志」的可追溯链条
