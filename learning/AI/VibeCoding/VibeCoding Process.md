
**核心**：把 AI 从“代码生成器”变成“受控的协作伙伴”。

它的整体流程和传统开发相似，但每个环节的**执行主体和协作方式**发生了根本变化。以下是一个从需求到上线的完整流程，融合了多个实战指南和编排框架的实践。

## VibeCoding 流程

按阶段划分，每份文档都回答一个明确问题，并标注 AI 读取优先级。

| 阶段 | 文档类别 | 核心文档 | 回答的问题 | AI 读取优先级 |
|------|----------|----------|------------|---------------|
| 0. 启动与定义 | 战略与范围 | 项目简报、范围定义、成功指标、假设与风险 | 为什么做？为谁做？不做什么？ | 高 |
| 1. 需求与规划 | 需求与验收 | PRD、用户故事、验收标准、优先级、数据模型概览 | 具体功能是什么？怎样算做完？ | 高 |
| 2. 架构与设计 | 架构与设计 | 技术架构、ADR、数据模型、API 契约、DESIGN.md、环境配置 | 怎么搭？用什么技术？接口怎么定？ | 高 |
| 3. 开发与执行 | 执行与协作 | AGENTS.md、TASKS.md、开发日志、上下文摘要、prompts/skills | 怎么做？先做什么？AI 如何协作？ | 极高 |
| 4. 测试与质量 | 质量与测试 | 测试策略、测试用例、验收证据、安全清单、性能报告 | 怎么验证？证据在哪？ | 高 |
| 5. 部署与上线 | 部署与运维 | 部署文档、CI/CD、环境变量、运行手册、回滚方案 | 怎么上线？出问题怎么办？ | 中高 |
| 6. 监控与迭代 | 迭代与知识 | 监控告警、反馈、Roadmap、Changelog、复盘、知识库 | 上线后怎么迭代？经验如何沉淀？ | 中 |

### 按文档类别归纳

1. **战略与范围类**  
   项目简报、范围定义、成功指标、非目标、假设与风险。

2. **需求与验收类**  
   PRD、用户故事、验收标准、优先级矩阵、待解决问题。

3. **架构与设计类**  
   技术架构、数据模型、API 契约、UI 设计规范、ADR、环境配置。

4. **执行与协作类**  
   `AGENTS.md`、`TASKS.md`、开发日志、上下文摘要、提示词库、技能库。

5. **质量与测试类**  
   测试策略、测试用例、验收证据、安全清单、性能测试报告。

6. **部署与运维类**  
   部署文档、CI/CD 配置、环境变量说明、运行手册、回滚方案。

7. **迭代与知识类**  
   Changelog、Roadmap、用户反馈、复盘文档、知识库、经验教训。

### 01 需求分析与规划

*AI 辅助定义“做什么”*

**目标：** **将模糊的想法转化为结构化的、AI 可执行的规格文档**。

**关键原则：** “文档先行，代码在后”——AI 在没有清晰文档时容易“臆想”架构。


#### 需求锚定与验证

先用自然语言向 AI 描述业务目标、用户价值和成功标准。可以借助 AI 进行初步的市场调研或用户需求验证。例如，有开发者先用 AI 抓取社交平台数据、生成问卷，验证了“大学生情绪记录与缓解”是一个真实需求后，才确定产品方向。

   - **模版**：[项目简报](template/.agents/specs/product/brief.md)
   - **要求**：定义问题、目标、用户与成功标准。该层定义不清时，后续全部内容将发生偏离。这是整个项目的“北极星”，AI Agent 在后续所有工作中都会引用它来判断方向是否正确。

#### 撰写 PRD

在 AI 协助下，将想法整理成正式的 PRD，明确**要解决什么问题、边界在哪里、如何验收**。同时，必须明确**非目标**，防止项目范围蔓延。

   - **范围定义**
     - **模版**：[范围定义](template/.agents/specs/product/scope.md)
     - **要求**：明确范围内事项、范围外事项、技术约束与本轮完成边界，用于控制范围扩张。AI 容易“过度发挥”，范围定义是防止此问题的第一道防线。
   - **产品需求文档**
     - **模版**：[产品需求文档PRD](template/.agents/specs/product/prd.md)
     - **要求**：将产品需求转换为结构化功能描述，明确对象、行为、输入、输出与边界，为后续验收与实现提供对照基线。面向 AI 的 PRD 有一个关键要求：验收标准必须可操作、可验证，禁止“体验良好”“性能优秀”这类无法验证的表述，必须写成“点击X按钮后，出现Y”这种可直接验证的动作-结果对。
     - **给 AI 的 PRD 与给传统工程师的 PRD 的关键差异**：AI 消费的 PRD 应删除商业价值论证、市场规模、KPI 汇报等对代码实现无影响的内容，只保留编码 Agent 写代码需要知道的信息。
   - **验收标准**
     - **模版**：[验收标准](template/.agents/specs/product/acceptance-criteria.md)
     - **要求**：将目标转换为可判定的验收项，使“已实现”成为可判断命题，为后续测试策略和证据映射提供基线。这是连接“需求”与“测试”的桥梁。

### 02 技术选型与架构设计

**目标：** **把需求转成一套能落地的技术方案，明确用什么技术、怎么分层、数据怎么存、接口怎么定**。

**关键原则：** 先定骨架，再写代码。技术选型由人拍板，AI 负责给候选和理由；架构、数据模型和接口一旦定下来，就当作契约冻结，后续按契约推进。

#### 技术选型

这个阶段是**在 AI 的帮助下，确定技术方案的骨架**。

- **技术栈选择**：向 AI 说明你的熟悉程度、项目需求和部署环境，让它推荐“最简单可行”的技术栈。例如，对于快速 MVP，AI 可能会推荐 Next.js + Supabase + Vercel 的组合，以实现低成本甚至零成本部署。
- **架构设计**：基于 `ARCHITECTURE.md`，与 AI 确认模块划分、数据模型和 API 接口。对于复杂项目，可以采用**契约冻结**机制：在开发前锁定核心接口定义，后续模块开发并行进行，避免冲突。
- **工具链配置**：配置好 AI 编程环境，如 Cursor、Claude Code、GitHub Copilot 等，并引入 Git 进行版本控制，建立分支策略和提交规范。

   - **技术架构**
     - **模版**：[技术架构](template/.agents/specs/design/architecture.md)
     - **要求**：写清技术栈和选型理由、系统分层、模块划分、目录结构与关键流程。这是整个系统的骨架，新代码要落在既定模块里，架构变更登记到 ADR。
   - **环境与配置**
     - **模版**：[环境与配置](template/.agents/specs/design/environments.md)
     - **要求**：列出各运行环境、环境变量与配置方式，说明本地怎么启动。密钥通过密钥管理注入，`.env` 不提交；缺必填变量时启动要快速失败。

#### 用户交互设计

先把界面长什么样、怎么交互定下来，避免开发时每个页面各写一套风格。文档里要写清设计原则、颜色与字体、间距、组件规范和交互细节，颜色和尺寸统一用 token 表达，不要临时自创。

   - **模版**：[UI 设计规范](template/.agents/specs/design/design-system.md)
   - **要求**：定义设计原则、颜色 / 字体 / 间距 token、组件规范与无障碍要求。写 UI 前先读，颜色和尺寸一律引用这里的 token。

#### 数据库设计

数据库设计要确定数据怎么组织。文档里要包含实体、字段、类型与约束，以及实体之间的关系和级联行为，还要考虑迁移方式和敏感字段的处理。字段命名和类型要统一，改结构时同步更新迁移与回滚方案。

   - **模版**：[数据模型](template/.agents/specs/design/data-model.md)
   - **要求**：定义实体、字段、关系与约束，说明索引、级联行为和迁移方式。涉及数据读写、迁移或接口设计前先读，保证命名与类型一致。

#### API 设计

API 设计要把前后端（或服务之间）怎么通信定死。文档里要包含通用约定、响应结构、错误码，以及每个接口的入参出参和示例。接口定下来后按契约冻结，改动走评审并同步更新文档。

   - **模版**：[接口契约](template/.agents/specs/design/api-contract.md)
   - **要求**：定义通用约定、响应结构、错误码与各接口详情。字段名、类型、错误码以本文档为准，契约冻结后修改必须走评审。

### 03 计划、任务与门禁

*把设计拆成可执行的小步，并设好检查点*

**目标：** **把架构与设计文档拆成一个个能独立完成、可验证的小任务，并在关键节点设好质量门禁**。

**关键原则：** 任务要小到一次能做完、一次能验完；门禁是硬约束，没通过就不进入下一步，判断权始终在人手里。

#### 计划

实施计划要回答“先做什么、做到哪一步算一个里程碑”。文档里要包含里程碑清单，每个里程碑写清目标、包含哪些任务、计划时间和状态；里程碑能对应到验收标准，方便判断阶段是不是真的完成。

   - **模版**：[实施计划模版](template/.agents/plans/template.md)
   - **要求**：列出里程碑、目标、包含任务与计划时间，作为阶段性交付的判断依据。每次的计划在 `.agents/plans/` 下按计划名新建文件，并登记到该目录的 README 清单里；进入下一阶段前，先确认对应门禁已通过。

#### 任务文档

任务文档是开发时唯一的任务来源。每个任务要写清目标、允许改动的范围、对应的验收项和产出，依赖关系也标出来。一次只领一个任务，做完、验完再领下一个，不要一次性把整张清单丢给 AI。

   - **模版**：[任务清单模版](template/.agents/tasks/template.md)
   - **要求**：把工作拆成可独立完成和验证的小任务，标注对应功能、依赖与状态。每次的任务清单在 `.agents/tasks/` 下按批次新建文件，并登记到该目录的 README 清单里；每次只领取一个任务，完成后更新状态再领下一个。

#### 质量门禁

质量门禁是给整个流程设的硬检查点，用来约束 AI 生成的代码质量。在需求、设计、开发、发布这些关键节点各设一道门，检查项要能直接判断，比如代码是否通过 Lint 和类型检查、关键模块是否经过独立评审、验收证据是否齐全；没通过就不进入下一步，避免 AI 一路生成、没人把关。

   - **模版**：[质量门禁](template/.agents/specs/plan-gate/quality-gate.md)
   - **要求**：定义各阶段的检查点与通过标准，作为进入下一阶段的前置条件。检查项要能判断，避免“体验良好”这类模糊表述。

### 💻 阶段三：AI 辅助开发与迭代（核心编码环节）

这是耗时最长的阶段，关键在于**控制 AI 的生成节奏，避免一次性生成大量不可控代码**。

**推荐的工作循环：**

1. **小步任务指派**：从 `TASKS.md` 中领取一个**小目标**（例如“实现用户登录接口”），而不是“完成整个后端”。要求 AI 在完成每个主要功能后停止，解释代码差异，并尽可能运行测试。
2. **AI 生成与人工审查**：AI 生成代码后，你必须**审查每一处变更**。重点关注：
   * **模块化**：是否生成了难以维护的“单体巨文件”。
   * **一致性**：新代码是否符合既定的架构和代码风格。
   * **安全性**：是否有明显的安全漏洞（如硬编码密钥、未验证的输入）。
3. **上下文管理与清理**：适时使用 `/clear` 或 `/compact` 等命令清理或压缩 AI 的上下文窗口，防止其因“记忆过载”而产生混乱输出。
4. **本地预览与调试**：每完成一个功能模块，就在本地（localhost）运行并测试，确保基础功能正常，再进入下一模块。
5. **独立评审**：对于关键模块，可以引入**独立的评审 Agent**，从不同角度审查代码，避免“自产自评”的盲点。

### 🧪 阶段四：测试与质量保证（从“Vibe Testing”到工程化验证）

Vibecoding 的测试策略需要结合 AI 的自动化能力和人类的判断力。

* **AI 生成测试用例**：你可以定义验收标准，让 AI 编写对应的单元测试、集成测试或端到端（E2E）测试。例如，一个名为 `Vibetest` 的工具可以从对话记录中提取功能需求，并使用浏览器自动化进行测试。
* **“Vibe Testing” 的实践**：这是一种 AI 驱动的测试新范式。AI 可以根据错误模式推测 bug 源头，甚至采用“多模型协同（Council of LLMs）”策略，用多个 LLM 生成测试用例，减少盲点。
* **人工验收测试**：对于涉及用户体验、业务逻辑边界的情况，必须进行人工测试。可以借助 AI 辅助梳理测试清单和启动流程。
* **代码质量红线**：引入**类型守卫**（如 Pydantic 强制校验）、**静态代码扫描**和**安全扫描**，作为 CI/CD 流水线中的强制关卡，让运行时类型错误和安全漏洞尽早暴露。

### 🚀 阶段五：部署与上线（从本地到生产环境）

Vibecoding 的部署流程可以非常平滑，许多 AI 工具和平台已支持对话式部署。

* **部署策略选择**：
  * **免费/低成本平台**：对于 MVP 或个人项目，可以使用 Vercel、Netlify、Cloudflare Pages、Render 等平台，通常有免费额度，部署流程简单。
  * **自托管/VPS**：当需要更多控制权时，可以部署到 VPS，使用 Docker 容器化，配合 Nginx 反向代理和 SSL 证书。
  * **对话式部署**：一些集成环境（如 WorkBuddy + CloudBase）支持直接通过对话完成部署，生成可访问的 URL。

* **CI/CD 集成**：为了确保部署的可靠性和一致性，建议配置 CI/CD 流水线（如 GitHub Actions、Jenkins）。流程通常是：代码推送 → 自动运行测试 → 构建镜像 → 部署到目标环境。AI 还可以辅助分析 CI 构建日志，甚至形成“修改代码 → 推送 → 触发构建 → AI 分析错误 → 修复”的自动化闭环。

* **上线前检查清单**：上线前务必确认：
  * **环境变量与密钥**：`.env` 文件是否已正确配置，且**未泄露**到代码仓库。
  * **域名与 DNS**：域名解析、SSL 证书是否就绪。
  * **数据库备份**：生产环境数据库是否已配置备份策略。

### 📊 阶段六：上线后监控与迭代

上线不是终点。Vibecoding 的优势在于快速迭代。

* **监控与反馈**：配置基本的应用监控（如日志、错误追踪），收集用户反馈。
* **数据驱动迭代**：根据监控数据和用户反馈，确定下一轮迭代的优先级。可以将新的需求再次输入到“需求锚定”阶段，开始新一轮的 AI 辅助开发循环。
* **知识沉淀**：将本次开发中总结的 Prompt、Skill、架构模式沉淀到项目的知识库中，让下一个项目的起点更高。
